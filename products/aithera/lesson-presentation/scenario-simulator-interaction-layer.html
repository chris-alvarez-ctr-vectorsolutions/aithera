Scenario Simulator · Part 2 — The Interaction Layer

Interaction Modes, Components & Prompts

A scenario has three parts: an open-ended context intro, an interaction layer where the learning happens, and a structured debrief. This document specifies the middle. It defines the interaction layer as a set of modes and states, for each, what a writer authors, what the platform provides, and which prompts run when.

Companion to the Build & Authoring Specification, which covers the end-to-end flow.
Status — For product + engineering Supported modes — Roleplay · Guided Arc · Observe/React · Teach-Back Authoring tool — Writer Studio
1

The interaction layer

Every scenario is the same three-part shape. The first part sets the scene and the third part evaluates and closes — both are standardized. The middle is where a learner acts and the system responds, and it takes a different form depending on what is being taught. That form is the scenario’s mode.

Part 1 · open

Context intro — a chosen modality

Exactly one intro modality per scenario, selected from a fixed set: video, story-highlight, narrated audio, reading, or none. Sets the scene, then hands off. Delivered by the shared SceneContext player via one intro.type field.

Part 2 · interaction
▲ this document

The interaction layer

Where the learner acts and the system responds. Its form is set by the mode — Roleplay, Guided Arc, Observe/React, or Teach-Back. This is the part that varies per scenario and carries the learning.

Part 3 · close

Debrief & close — evaluated and structured

A separate evaluation engine scores the session against the authored rubric and produces the results surface, followed by the exit. Standardized across all modes (§7).

One skeleton, filled per mode

Every mode is built from the same sub-phases. Engage, React and Coach form the loop — the three things authored per turn — and Gate is the hinge that runs the loop again or advances. Enter and Exit are the transitions in and out. Naming these gives writers and developers one vocabulary and a precise unit for “which prompt runs when.”

ENTERthe way in →
↺ the loop · repeats 1–N
ENGAGElearner moves → REACTsystem responds → COACHreads & nudges
→ GATErepeat or advance? → EXITthe way out

↺ Gate is the hinge: while its condition isn’t met, it sends the learner back to Engage for another pass — Engage 1 → React 1 → Coach 1, then Engage 2 → React 2 → Coach 2, and so on. When the condition is met, it advances to Exit.

How many times the loop runs is set by the mode: a conversation runs ~4–6 turns; a guided arc runs a fixed beat sequence; observe/react runs once per media segment (1+); teach-back runs one long pass with grading in the background.

The transitions the author shapes

Three boundaries move the learner between phases. Gate is the one with real logic — requirements and conditions; the other two are handoffs the author still shapes with a line of copy. Modes with an ordered set add one more: the sequence itself.

TransitionWhat it isWhat the author sets
Enter → LoopThe way in from context to the first passOpening question / reflection; the CTA that starts practice
Gate every passThe hinge — repeat the loop or advanceRequirement, nudge cap, fallback, completion condition (hard or soft)
Loop → ExitThe way out to the debriefThe “Analyzing…” handoff copy
Sequencing some modesWhich phase, beat, or segment comes next inside the loopThe order of phases/beats (Guided Arc) or media segments (Observe/React). In Guided Arc, the phase-to-phase hand-off is a locked verbatim signpost, delivered word-for-word — not free coach copy
2

The six phases, up close

The skeleton is more than a diagram — each phase is a distinct authoring surface with its own decisions. Across the six, a scenario carries roughly three dozen variables that an author sets (with engineering on the locked pieces). This section takes each phase in turn: what it does, what must be decided, and an example.

1

Enter · 6 decisions

Orient the learner and move them into the interaction.

What the author decides
  • Intro modality — one of video, story-highlight, narrated audio, reading, or none
  • Intro content — the assets for that modality (clips + captions, story text + highlight anchors, or a narration script)
  • Establishing card — eyebrow, title, and the one-line framing
  • Opening image — what the learner sees on entry, so no one lands on an empty stage
  • Opening question — the coach’s first prompt
  • Opening reflection — whether there is one, and the ideas it must draw out (in-context, not a barrier)
Example
Scenario · Check-in
Kendra’s Room
A hard conversation with a friend who’s been struggling.
CoachBefore you go in — what do you want this conversation to actually do?

Kendra (video intro): establishing card, then the coach’s opening reflection — surfaced in-context.

2

Engage · 6 decisions

The learner’s move — the thing they actually do.

What the author decides
  • Engage type — speak in character, answer the coach, react to media, or teach a topic (set by the mode)
  • Input modality — type, talk (speech-to-text), or both
  • Affordance & placeholder — the prompt copy in the input bar
  • Turn shape — a single line versus a free response; length expectations
  • Repetition — how many times Engage runs (turns, beats, segments, or one continuous pass)
  • Off-script tolerance — how empty or curveball input is handled
Example
KendraIt’s fine, seriously. I just needed to unwind.
Say something to Kendra…↑
TypeTalk

Kendra takes a typed line in character; Teach-Back adds a Talk / Type choice.

3

React · 6 decisions

The system’s response to the learner’s move.

What the author decides
  • Response source — a model-voiced character, the next authored beat, the next media segment, or a live grade
  • Character (if any) — voice, backstory, what they know, and what they’ll never do
  • Reaction map — when/then rules that steer how the response lands
  • Emotional state — the character’s mood, shown and shifting across the scene
  • Sequencing — single-shot versus multi; which beat or segment comes next
  • Constraints — length, tone, and what the response must never reveal
Example
KendraWhy does everyone keep making this a thing? I’m handling it.emotional state → defensive
▶▶▶

Varies by mode: a model-voiced character reply (Kendra) — or the next authored media segment (HazMat).

4

Coach · 7 decisions

The coach reads the exchange and nudges.

What the author decides
  • Persona & voice — who the coach is and how they sound
  • Feedback shape — length and structure (e.g. a short read plus one question)
  • What it reads against — the assessment dimensions or rubric
  • When it speaks — every turn, in the same turn as React, or only when the learner stalls
  • Nudge style — an open nudge versus a concrete one
  • Right-answer delivery — for a knowledge check, stating the correct answer plainly
  • Safety overrides — a crisis or safety floor that supersedes everything else optional
Example
CoachYou kept it warm and didn’t push — good. She’s not ready to admit much yet.

Who in her life could you point her toward?

Kendra: a read on the exchange plus one concrete nudge, aimed at the learner’s weakest dimension.

5

Gate · 6 decisions

Decide whether to advance — and on what terms.

What the author decides
  • Hard or soft — a blocking requirement versus always-advance (author’s choice; a scenario may use both)
  • The requirement — what the learner must do to clear a hard gate
  • Nudge cap — how many nudges before the gate relents
  • Fallback — what happens at the cap (teach the point, then move on)
  • Soft advance condition — learner-driven, a coverage count, or automatic
  • Completion condition — what ends the interaction as a whole
Example
🔒  Required move not reached — connect Kendra to real help · nudge 1 of 2
✓  Soft gate — nudge given, advancing

Author’s choice: a hard gate holds until the required move (Kendra); a soft gate nudges once, then moves on (HazMat).

6

Exit · 7 decisions

Close the interaction and hand off to evaluation.

What the author decides
  • Completion trigger — what hands off to the close
  • Progress summary — which signals are emitted (moves, coverage, dimension results)
  • Evaluation rubric — the competencies measured and what strong and weak look like
  • Output shape — strengths + growth, or a coverage score
  • Playbook — guaranteed takeaways, identical for every learner optional
  • Resources — domain-specific support for the subject optional
  • Proficiency record — the exit signal’s contents and the next learning object
Example
StrengthsLed with empathy; stayed non-judgmental.
GrowthName the specific risk sooner.
Teach-Back · 6 of 10 topics covered

Output shape varies: strengths + growth (Kendra), or a coverage score (HazCom) — both from the evaluation engine.

The phases are the authoring checklist: six surfaces, each with its own decisions, before a single line of the scenario is generated. A mode fixes some of these (Roleplay always has a character; Teach-Back never does); the rest are the author’s to set per scenario.

4

The spine — shared by every mode

These components are identical across every mode. A mode inherits all of them and implements none; it supplies only its own content and its slot-filling logic.

  • The coach. One AI coach — a voice in a panel that rises over the stage — is present in every mode. Feedback always lives here. A character is separate and optional; the coach is not.
  • The stage + coach-panel shell. Topbar, the stage/coach two-surface layout, and the input-bar states. A mode supplies content into this chassis and never rebuilds layout.
  • The per-turn JSON contract. Every model response is strict typed JSON, never prose. The contract, off-script handling, learner-safety floor, and source grounding are pinned in ENGINE_SECTIONS and are read-only to authors — the boundary between authoring and runtime.
  • Parse, repair, or fall back. repairJson corrects format slips without a second call; parseTurn validates and, on failure, returns a safe coach line so the session never breaks.
  • The proxy Worker. One Cloudflare Worker holds the API key and enforces a model allowlist, token cap, and CORS allowlist. Every mode posts the same {model, system, messages} shape. Conversation and evaluation run on claude-opus-4-8; fast grading runs on claude-haiku-4-5.
  • The context player. SceneContext renders the chosen intro modality (audio, reading; video has its own cold-open player), switchable by one field.
  • The authoring registry & store. AitheraStudio — register / get / list plus per-mode namespaced storage (draft / published / library). A mode publishes here and its learner page reads it on load.

The spine is type-agnostic by design: the Writer Studio shell reads only a mode’s public surface and holds no knowledge of any specific pedagogy.

5

The mode contract

A mode is a single object implementing the surface below, registered once. This is the contract every mode conforms to — the definition of what a mode owes the platform in exchange for the spine.

every modeuniversal optionalpresent only if the scenario needs it mode-specificunique to one schema 1+repeatable — count is authored

The mode surface — what AitheraStudio.register() takes

// a mode = a scenario type. One object, registered once.
{
  id, label, icon,               // identity + switcher display

  // ---- WHAT THE WRITER FILLS ----
  DEFAULT,                        // the scenario schema, expressed as data
  sections, renderFields(sec, H),   // the Writer Studio form: groups + field rendering
  lints(s),                        // authoring checks surfaced before publish

  // ---- HOW DATA BECOMES PROMPTS ----
  compile(s),                      // scenario data → the prompt(s) the platform will run
  ENGINE_SECTIONS,                // locked output contracts — read-only to authors
  highlightStrings(s),           // maps prompt text back to the field it came from

  // ---- PERSISTENCE + RUNTIME WIRING ----
  normalize(s), isValid(s), merge(draft),  // schema migration + validation
  store,                          // draft/published/library (shared machinery)
  previewUrl(),                    // the learner page that renders this mode
  playtest,                       // optional in-studio dry run
}
ENGINE_SECTIONS are locked. An author writes a scenario’s content — the situation, character, rubric, takeaways — never the output-format contract, off-script handling, or safety floor. This is what lets authors work in plain language without being able to break the runtime.
Prompt count is the platform’s decision. Most modes compile to a single prompt. When a mode’s work genuinely splits — as with teach-back’s separate calibration, grading, and closing — the platform compiles the additional prompts and wires them. Authors are not asked to reason about this; the system is opinionated about when it applies and can surface the compiled prompts for reference.

The modes in detail

Each card fills the skeleton, lists the authored inputs with their cardinality and scope, and states why each piece exists. Field names are the real schema fields. Swatch legend:

Authored by a content writer Generated live by the model Locked platform contract
Mode A

Roleplay

The learner enters a scene and speaks as themselves to a model-voiced character, one line at a time, while the coach reads each exchange and nudges. Example: Kendra — checking on a friend showing signs of a drinking problem.

schema: action-practice
Enter every mode

Chosen intro modality → establishing card → the coach’s openingQuestion. An optional opening reflection can draw out required framing in-context.

Engage ~4–6×

The learner types one scene line, in character, across a natural conversation of roughly 4–6 turns (pacing.sceneLines).

React

The character replies once — narration + dialogue with an emotionalState — steered by the reactions map and styleNotes.

Coach

In the same turn, the coach debriefs the exchange and aims its nudge at the weakest scored dimension.

Gate optional

Configured here as a hard gate: the scene cannot resolve until the learner reaches the required move (gate.requirement).

Exit

Hands the full transcript and dimension results to the evaluation engine (§7).

Authored inputs — action-practice schema

{
  title, learnerName, characterName, courseContext,   // required
  setup,                                // the character card = setup + reactions + styleNotes
  pacing: { sceneLines:'4-6', duration },   // tunes the conversation length
  openingImage, openingQuestion,
  dimensions: [{ name, strong, weak }],    // the silent rubric       // 1+ (Kendra: 3)
  reactions:  [{ when, then }],            // character reaction map    // 0+
  misconceptions: [{ belief, consequence }],                              // 0+ · optional
  gate: { requirement, notSuccess, teach, nudgeOpen, nudgeConcrete, fallback },  // optional
  coachVoice: { persona, guidance },
  completion: { condition, resolutionExample },
  intro: { type, … },                     // one modality
  elevatedStakes: true,                  // OPTIONAL · Kendra-specific: locks a crisis-line floor
  playbook: [{ title, body }],            // OPTIONAL guaranteed takeaways   // 0+ (Kendra: 7)
  resources, references              // OPTIONAL · domain content (Kendra: substance-use + crisis support)
}
→Why this shape: a single prompt keeps the character consistent and lets the model carry turn-to-turn memory. Silent dimensions let the coach target the right weakness without turning practice into a visible test. The hard gate names the one behaviour the scenario refuses to let a learner skip. When present, the playbook and resources are guaranteed and identical for every learner — content too important to leave to generation, and specific to the scenario’s subject.
Mode B

Guided Arc

An authored, phased arc with a live coach throughout. The learner moves through an ordered sequence of phases — reflect, then reason about the law, then step into the person's experience — alternating Practice (the learner reasons; the coach withholds teaching) and Learn (the coach lands the point), and finishing in a live scene where they decide what to do. Fixed verbatim signposts carry the hand-off between phases; a guaranteed SME playbook closes it. Example — and current reference build: Marshall (bystander intervention), marshall-live-v3.html.

schema: guided-arc
Enter

Chosen intro modality (Marshall: a video cold-open with a read-along transcript) → the coach’s opening reflection, which is calibration only, not evaluated.

Engage per phase

The learner answers the coach through each phase — as themselves. In the closing scene they instead act: input widens from “what do you say” to “what do you do?”

React

The coach advances to the next phase on a verbatim signpost cue. In the closing scene, the consequence of the learner’s action plays back in an emphasized narration tier before the coach debriefs it.

Coach

Alternates Practice (teaching withheld to a single Socratic probe) and Learn (the coach opens with a fixed “talk it through” line, then lands the point). The law phase carries an authored right answer the coach states plainly.

Gate mixed

The law phase gates on reaching the correct legal conclusion; the open phases (reflect, empathy) always advance.

Exit

After exactly two scene actions (with a scripted escalation between them), the arc closes on a guaranteed 9-component SME playbook shown identically to every learner.

Authored inputs — guided-arc schema (v3)

{
  title, course, learnerName, characterName,     // required
  framing, learnerRole,                     // the premise + the role the learner plays
  establishing: { eyebrow, title, sub }, intro: { type, … },  // one modality
  reflection: { prompt, feedbackGuidance },   // non-evaluated warm-up (verbatim prompt)
  phases: [                              // 1..N Practice→Learn phases, reorderable
    { id, label, signpost, prompt,          // signpost + task shown VERBATIM
      hasRightAnswer, talkItThrough,         // verbatim opener of the teaching turn
      calibration:[{ tier, guidance }], throughLine },  // tiers + the graded conclusion
  ],
  scene: {                               // OPTIONAL live action console
    pivot, setup:[{ speaker, kind, text }],    // verbatim pivot + break-room beats
    sayDoSplit, actionCount, outcomes:[{ tier, narration }],  // consequence tiers
    debrief:{ talkItThrough, points } },
  playbook: [{ title, body }],            // guaranteed takeaways   // (Marshall: 9)
  resources, elevatedStakes                 // OPTIONAL · domain content · crisis floor
}
→Reference build: Marshall v3 is this schema's shipped DEFAULT — the Studio authors it, and it runs on the generic guided-arc-live.html (with nothing published, that page plays the Marshall default). The stand-alone marshall-live-v3.html remains as the frozen reference the schema was validated against: compile(DEFAULT) reproduces its hand-tuned system prompt.
→Why this shape: some content is a guided lesson with decision points, not an open roleplay — the arc must land specific points in a specific order, and a live coach fills the gaps so the path stays responsive without losing its authored precision. Note that Guided Arc now borrows from Roleplay at the finish: its optional closing scene is a genuine in-character moment, which is why the two modes overlap where they used to be distinct.
Mode C

Observe / React

The learner watches authored footage and the coach probes what they saw and felt. Media segments are the spine; the coach fills the gaps. Example: HazMat — reading a scene from footage of a hazardous-materials call, across watch-then-react chapters.

schema: observe-react
Enter

Establishing card → the first segment plays as the cold open.

Engage 1+ per segment

The learner reacts, as themselves, to what they just watched.

React

The next authored segment advances the scene; a chapter-advance signal returns the learner to Observe.

Coach

Probes against the authored structure. An affective beat — “how did that make you feel?” — validates instinct before asking what should have happened.

Gate optional

Configured here as soft: a weak answer draws a nudge, then advances.

Exit

A synthesis beat closes the run; results hand off to evaluation.

Authored inputs — observe-react schema

{
  title,                                // required
  segments: [{ src, label, caption }],     // the media spine + narration   // 1+ (HazMat: 3)
  openers: [{ segment, line }],           // scripted coach line returning from a segment  // 0+
  dimensions: [{ name, strong, weak }],    // the rubric              // 1+
  openingQuestion,
  gate                                    // OPTIONAL advance rule
  // no character; the media is the stimulus the coach reacts to
}
→Why this shape: some skills are about reading a situation, not conversing in one. Authored media is the stimulus the coach reacts to — it takes the place of a character while the coach stays constant. The affective beat is deliberate: naming a gut reaction before analysis is the pedagogy, so it is authored as its own step.
Mode D

Teach-Back

The learner teaches a subject back in their own words while a live rubric grades coverage. The learner produces and the system assesses — the inverse of being coached. Example: HazCom — teaching a Hazard Communication course back across its topics.

schema: teach-back
Enter

Title → a brief calibration chat that gauges readiness and unlocks teaching. No scoring here.

Engage continuous

The learner teaches topics in any order, by voice or text — one long move rather than discrete turns.

React

A live grade decides which topics an utterance covered; covered topics resolve and the coverage meter updates.

Coach

Speaks only when the learner stalls: a category-level hint that never names the topic.

Gate optional

Ends on full coverage, or when the learner chooses to finish. Framed by count, never by omission.

Exit

Coverage results hand off for the closing score and note.

Authored inputs — teach-back schema

{
  title, subject,                        // required
  topics: [{ short, full, synonyms }],      // the rubric — full = matched against; synonyms = accepted phrasings  // 1+ (HazCom: 10)
  calibrate: { openingQuestion, coachGuidance },
  grade: { rules },                        // grading judgment / disambiguation
  close: { guidance }
}
// compiles to THREE prompts: calibration · live grading · closing
→Why this shape: teaching to learn is a different act than being coached, so the mechanics invert — the learner produces and the system assesses. Grading runs on a fast model so a correct sentence resolves a topic within about a second, while calibration and closing use the stronger model. Coverage is stated as a count because a legible score is the point. This is the template for any mode that assesses what a learner produces.
7

Evaluation & close

The interaction layer hands off to a standardized close. Evaluation is deliberately separate from the in-scene coach: the coach guides during practice, and an independent engine judges the result. This keeps assessment objective and consistent across every mode.

The evaluation engine

  • Summarized progress in. Each part of the interaction contributes a compact record of what the learner did — moves, coverage, dimension results — not raw transcript. The engine reads this summary, keeping the evaluation prompt separate from and lighter than the coach prompt.
  • Judged against an authored rubric. The author defines what the scenario measures and what strong and weak look like. The engine evaluates the summarized progress against that rubric — the author shapes the rubric, not the phrasing of the verdict.
  • Objective guidance out. The engine returns learner-facing results: strengths and growth areas, or a coverage score, grounded in the rubric and the learner’s own actions.

The close then renders standard surfaces. Two are universal; two are optional and authored per scenario:

ElementWhat it isScope
Results surfaceStrengths + growth, or a coverage score with a short note — the evaluation outputevery mode
ExitEmits a proficiency record and advances to the next learning objectevery mode
PlaybookGuaranteed takeaways, identical for every learner regardless of pathoptional
ResourcesDomain-specific support and references for the scenario’s subjectoptional

The proficiency record — competencies with evidence, or a score — is the single output that makes any scenario, in any mode, composable as a learning object downstream.

The whole system in one line: a scenario is an authored context intro, an interaction layer in one of four modes, and an evaluated close. The context and the close are shared and standardized; a mode differs only in how it fills the skeleton — ENTER → ( ENGAGE · REACT · COACH ) × N ↺ GATE → EXIT — and everything under the spine is inherited.
