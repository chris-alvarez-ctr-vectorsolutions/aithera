Decided — 2026-08-18 · this proposal was not adopted

The envelope was declined for V1 as too much complexity, and a generic “trauma-informed response” block — always on, every scenario — was judged sufficient in its place. answer_shape was deferred rather than declined: ideal_response is the proxy today, and the agreed next step is to test whether that holds before adding a field.

Worth recording honestly, because it cuts against the case made below: an always-on block covers more than these flags did. Our own go-forward route armed no learner-safety floor at all unless a flag was set, which was fixed separately — so the flags are properly an escalation on top of a floor, not the only thing between a scenario and silence. What the generic block does not replace is the per-scenario portrayal layer. Full consequences: Meeting Outcomes.

One key in the schema: extension envelopes for Scenario CML v4

Our scenarios carry a handful of fields v4 can't say yet — whether a step has a right answer, and safety flags for threat, crisis, and minors content. Because the schema rejects every unknown field, our only handoff option today is deleting them, and the file silently loses real behavior. The proposal is one sanctioned extensions container, under load-and-ignore rules. No engine work is being requested.

Proposing side UX Universal (Editor + prototype player) Change to lo_cml_v4.schema.json + the loader Size one allowed key, two objects Whose call POC V4

The whole proposal read this, skip the rest

Allow one property, extensions, on content and on each practice: an object of namespaced keys (vector:*), values any JSON. The rule that makes it safe: an engine MUST load a document whose extensions it does not implement, and MUST ignore them. Everything else stays exactly as strict as today.

§1 · Why

Four fields, and what deleting them costs

These are authored content classification — not prompt text, so they don't violate the content-only constraint. Each one already drives real, testable behavior in the UX Universal player, which is the reference implementation you can diff against when you pick one up.

FieldTypeWhat it drivesWhen it's deleted
practice.answer_shape "determinate" | "open" Whether the coach lands a conclusion plainly (graded step) or deepens the learner's own answer (reflection step). Reference: mix-arc.js / guided-arc.js teaching-verb switch. Every step reads as graded — the coach delivers verdicts on reflection steps, which defeats them.
content.elevated_stakes boolean Arms the 988 crisis floor — locked crisis-resource behavior when content is suicide/crisis-adjacent. Reference: CRISIS_FLOOR, js/scenario.js. The floor never arms. Nothing indicates it was ever there.
content.threat_content boolean Arms the locked threat-content section (escalation/violence handling; workplace-violence scenarios). Reference: THREAT_SECTION, mix-arc.js / branching-arc.js. Same — silent.
content.involves_minors boolean Arms the minor-protection floor (school / bullying scenarios). Reference: MINOR_SECTION, ensemble-arc.js. Same — silent.

The safety point, plainly

Without the flags, a workplace-violence scenario loads and runs with no crisis floor and no trace that one existed. That is not a formatting difference — it is a silent safety regression, and it is why we are raising this now rather than batching it with nice-to-haves.

§2 · The shape

Before and after, on your own Marshall scenario

Today — flat field, whole document rejected

"practice": {
  "mode": "coach_inquiry",
  "answer_shape": "open",   ← unknown field:
  "purpose": "…",                load fails
  …
}

Proposed — enveloped, namespaced, ignorable

"practice": {
  "mode": "coach_inquiry",
  "extensions": {
    "vector:answer_shape": "open"
  },
  "purpose": "…",
  …
}

Measured on our port of marshall.lo.json with the extension values authored in: as flat fields, the loader rejects at every path that carries one — one per practice plus one per content-level flag, scattered through the document. Folded into envelopes, every one of those rejections collapses to exactly one key kind — extensions. That single allowlisted key is the entire schema change. Both shapes are generated by js/scenario-v4.js (stripExtensions / foldExtensions), so you can reproduce the diff on any scenario rather than take the count on faith.

Your strictness survives — that's the point of the envelope

additionalProperties: false stays everywhere else, so a typo'd final_wrod still fails loudly. There is exactly one place vendor data may live, its keys are namespaced, and your §9.2 content lint applies inside it like everywhere else.

§3 · What this is not

Not a request to build anything

  • No engine work now. Load and ignore. Each field becomes yours to adopt individually, whenever — or never.
  • No open-ended schema door. One container, namespaced keys, must-ignore semantics — the same pattern xAPI, FHIR, and HTTP headers use for exactly this problem.
  • No spec archaeology when you do adopt one. Each extension ships with why it exists, what ignoring it costs, and a runnable reference implementation in the UX Universal player to diff against — so when you implement it, it behaves the same in both players by construction.

The alternative to this mechanism is what we do today: strip the fields per handoff and re-negotiate every future field one at a time, with each one blocking until decided.

§4 · Try it

Generate the exhibits yourself

The Editor's Dev handoff panel (Universal Scenario → Debrief & Close) downloads both profiles of any scenario:

  • <id>.lo.json — loads in your engine today: extensions stripped, revalidated against your loader's rules, with each removal and its cost listed.
  • <id>.proposed.lo.json — the enveloped shape this page proposes, byte-ready for a schema spike.

The validator behind both is a vanilla-JS port of your schema + the §9.1 loader rules + the §9.2 lint (js/scenario-v4.js; also runs as node js/scenario-v4.js <file>). It validates all 11 of your shipped scenarios clean, and 46 negative tests confirm it rejects what your loader rejects.
