How the voice input behaves

The idea

The mic is an alternative input for the same reply, not a separate mode. It sits inside the existing composer, next to send, so wherever a learner can type to the coach they can also speak. Speech fills the field; the learner still reviews and taps send.

Mic + Send — why this model

A mic inside the field plus a separate send button. Both are clearly buttons (the old decorative comment icon is retired). Crucially, tapping the mic appends to whatever's already in the field — so a learner can type part of a reply, then finish it by voice, or dictate a first pass and keep talking to add more. That append ability is why this beat the single morphing-button option.

The lifecycle

Idle. A quiet mic at the right edge of the field. Typing works exactly as before.
Listening. The field glows, a live equalizer animates, and words stream in as provisional (muted) text. Tap to stop.
Review. On stop, the transcript settles into normal editable text and focus lands in the field — fix a word, or tap the mic again to add more.
Send. Same send as always. A small mic glyph next to the You label marks speech origin (a design option — easy to drop).

Graceful when there's no mic

Where the browser supports the Web Speech API (Chrome, Edge, Safari) and mic access is granted, the mic does real dictation. In production, if the browser can't do speech the mic simply doesn't appear (no dead affordance). Here in the prototype it falls back to a sample dictation so the interaction is always demoable — the Play sample link runs that same demo on demand.

Where it lives

This prototype and the real pages now share one implementation: js/sim-voice-input.js. It's a drop-in enhancer — given a composer's field, send button and hint, it adds the mic. Adopted in scenario-live.html (all five converged scenario types) plus action-practice, story-highlight and teach-back. Any new coach-typing surface adopts it with one line.
