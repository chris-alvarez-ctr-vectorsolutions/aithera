Aithera · Scenario Simulator · Data & engine contract

One JSON skeleton. Five types. One engine that reads a dozen fields.

This is the data model and engine read-contract behind the working scenario simulator — proven across five runtime types (part of a seven interaction-type family) in a shipped prototype. It's offered so the production engine and its JSON can build on what already works, not as a spec to adopt wholesale. Take the parts that earn their place; diverge with cause.

The headline

It's the same structure everywhere, with additive fields — not five different structures

The most important thing to know before designing anything: every scenario type — no matter how different it looks to a learner — compiles down to one runtime shape: a scenario object carrying a phases[] ladder. The player engine (js/sim-player.js) only knows how to drive that one shape. So the differences between types are "extra objects hanging off the same skeleton" and "the same slots filled differently" — never a different backbone.

That constraint is the whole design. It's why adding the seventh interaction type didn't fork the engine, and it's the single idea most worth carrying into a fresh build: pick one runtime shape the engine drives, and make every authoring format normalize into it.

Two JSON layers — don't conflate them read first

Authored source is what a human edits and what the tool exports — it differs per type (mix-arc authors beats[]; branching/ensemble/scene-sweep author phases[] directly). Runtime is what the engine drives — the normalized phases[] ladder below, produced by type.toRuntime(source). The export you'll receive is the authored source; the runtime is derived from it at load. §6 covers exactly how.

§1 · The shape

The one runtime shape the engine drives

Verified by dumping toRuntime(DEFAULT) for all five types. Every runtime object shares the same common core plus exactly three engine-added keys (phases, opening, sceneLineCaption). The additive blocks at the bottom appear only on the types that need them.

Runtime scenario object — annotated

{
  // ── common core · every type, carried from the authored source ──
  title, course, learnerName, characterName,
  framing, learnerRole, establishing,
  intro:      { type: 'reading'|'audio'|'video', audio:{…}, video:{…} },
  voice:      { persona, guidance },
  reflection: { prompt, feedbackGuidance, enabled },   // the warm-up
  playbook:   [ … ],   resources: [ … ],

  // ── added by toRuntime() · every type ──────────────────────────
  phases:  [ /* the ladder — see §2 */ ],
  opening: [ "…reflection warm-up bubble(s)…" ],  // may be [] (boots into phase 1)
  sceneLineCaption: "You",

  // ── additive · only the types that need it ─────────────────────
  state?:    [ { key, label, initial } ],            // mix · branching · ensemble · guided
  cast?:     [ { name, baseline, driver, reactions[], … } ], // branching · ensemble
  canon?:    { … },                                  // branching · ensemble (continuity facts)
  coverage?: { required, total },                   // scene-sweep only
  hazards?:  [ … ],  decoys?: [ … ],  scene?: { … }  // scene-sweep only
}

§2 · The phase

The phase skeleton — the unit the ladder steps through

A phase is one rung of the ladder. There are three authored phase flavors, but they collapse to one skeleton the engine reads. The engine cares about a small subset (§3); the rest of a phase feeds the prompt compiler (§4).

Phase object — the engine-relevant fields

{
  id: "meeting",
  world: "coaching" | "scene",        // scene → learner faces a character; coaching → learner faces the coach
  counterpart: "Ray" | "" | "Narrator",  // who the learner faces in a scene
  maxTurns: 6,                            // turn cap — the APP owns advancement, not the model

  entry: {                               // the LOCKED, app-authored open of the phase
    bridge: "", bridgesByTier: { STRONG:"…", NEUTRAL:"…" },  // prior tier picks the opener
    signpost: "…", prompt: "…",
    beats: [ { speaker, kind, text, name? } ],  // scripted scene open
    cta: "Step into the room"
  },

  calibration: [ { tier: "STRONG", guidance: "…" } ],  // tier vocabulary (→ prompt)
  debrief: { talkItThrough: "…", points: "…" },        // talkItThrough = the verbatim teach-opener

  transitions: [                          // tier-routed next rung + state writes
    { onTier: "STRONG", next: "escalation", set: { disposition: "steadied…" } }
  ]
}

Two authored variants ride this same skeleton: a rich beat phase (mix-arc & guided) also carries type, character, media.segments[], hasRightAnswer, throughLine; a perception phase (scene-sweep) carries kind:"spot"|"act"|"prevent" and flat signpost/prompt that toRuntime folds into entry. The engine ignores the extras — they're prompt fuel.

§3 · The contract

What the engine actually reads — the whole contract fits on one screen

This is the tightest, most transferable part. The entire ladder engine reads only the fields below. Everything else in the JSON is either the model's job (prompt) or a render surface's job (§7). If your engine honors this contract, any of these scenarios plays.

The sim-player.js read-contract
FieldRead byWhat it decides
scenario.phases[]whole engineThe ladder. The app indexes it by state.phaseIdx — the app, not the model, is the source of truth for which rung is live.
phase.maxTurnsrunArcEngineThe turn cap. At the cap the app forces the model to resolve and report — it can't run long.
phase.worldapplyDeliver"scene" flips the input target to the character and enters scene mode; else coaching.
phase.entry.*entryBeatsForThe locked opener. bridgesByTier[prevTier] selects the bridge; then signpost, prompt, scripted beats.
phase.media.segments[]entryBeatsForLocked stimulus cards — a clip (video src) or a forwarded message — shown before the coach speaks.
phase.transitions[]{ onTier, next, set }closePhaseOn phase close, the recorded tier picks a transition → the next phase id, and writes session state.
phase.debrief.talkItThroughrunArcEngineThe verbatim teach-opener. When the model's turn starts with it, the app knows the phase is closing.
phase.counterpartapplyDeliverNames the character the learner faces (a non-"Narrator" scene counterpart).
scenario.state[]{ key, label, initial }arcStateBlockSession variables surfaced on the per-turn [SYSTEM STATE] line and written by transitions.
phase.kind + ctx.outcomeBlockarcStateBlock (optional hook)The one extensibility seam: a custom render surface (scene-sweep) opts in on kind. No hook → nothing runs, so conversational types stay byte-identical.

The load-bearing idea: the app owns advancement, the model owns voice

The model never decides which phase is next or when to move on. It returns a turn (dialogue + an action/tier); the app reads the cap, records the tier, applies transitions[], and appends the next locked entry. This is what keeps a live-LLM scenario on rails without scripting every branch — and it's the reason the same ~220-line engine drives a coaching chat, a role-play, a multi-character ensemble, and a spot-the-hazard canvas.

§4 · Two outputs

Every type emits two things: data (JSON) and a prompt (string)

A common trap when building an engine is to treat "the scenario" as one blob. Here it's deliberately two:

  • toRuntime(source) → a JSON object — the phases[] ladder the engine mechanically drives (§1–§3). Structured, diffable, small.
  • compile(source) → a system-prompt string — the model's instructions: the arc, the character models, the guardrails, the JSON turn contract. This is where each type's personality actually lives.

Most of the per-type divergence is in the prompt, not the data. The JSON structures look more alike than the types behave. Concretely, the compiled prompt sizes we measured:

compile() output — always a string, never JSON
TypePrompt sizeWhat bloats it (beyond the shared engine rules)
mix-arc~18.1k charsThe neutral baseline — composed beats, one voice.
scene-sweep~22.2k charsThe coverage contract, hazard rubric, look-again nudging.
guided-arc~24.3k charsCompiled via mix-arc after toMixArc() (§5).
branching-arc~32.4k charsTier-contingent bridges, the cast model, the threat floor.
ensemble-arc~37.9k charsMultiple cast models, earned disclosures, the minor-safeguarding floor.

Design takeaway: keep the data model boring and shared; let the prompt carry the variety. A field in the JSON should exist because the engine or a surface reads it — not because the model needs to be told something. Model instructions belong in the compiled prompt.

§5 · Native vs recipe

Two ways a type reaches the engine — and why the split matters

Not every type is a peer. Four are native: they own their toRuntime + compile and play directly on the shared engine (mix-arc, branching-arc, ensemble-arc, scene-sweep). One is a recipe: guided-arc has no ladder of its own — it expresses itself as a mix-arc scenario via toMixArc(source), then plays natively as mix-arc.

You can see the funnel in the data. Dumping guided-arc's runtime keys shows they're mix-arc's keys — it gained beats, state, threatContent, involvesMinors that its own authored source never had:

The recipe funnel, observed

guided-arc AUTHORED keys:  … phases, scene, contextSource, previousLO
                          // no `beats`, no `state`, no ladder
        │
        │  toMixArc(source)   // rewrite into a mix-arc scenario
        ▼
guided-arc RUNTIME keys:   … state, beats, threatContent, involvesMinors, phases, opening, sceneLineCaption
                          // now indistinguishable from a native mix-arc runtime

Why keep the split instead of funneling everything through mix-arc? Because the funnel is lossy. Branching's tier-routed transitions, ensemble's cast + earned disclosures, and scene-sweep's whole perception subsystem have no mix-arc equivalent — a round-trip would flatten them. The rule that emerged: reserve the recipe path for types that are genuinely a special case of another; let rich types own their runtime. A production engine benefits from the same rule — one canonical runtime, but don't force every authoring model through a lossy adapter to reach it.

§6 · The migration seam

normalize() is a version firewall — and it's what the export goes through

Every type has a normalize(source) that fills defaults and forward-migrates older authored JSON on load — mix-arc's migrateV2, guided-arc's beats→phases lift. This is why an export from months ago still plays through today's engine: it's re-normalized on the way in. If you build a fresh engine, budget for this seam — it's what lets authored content outlive schema changes.

How to read the export you'll receive for the dev team

The authoring tool's Export button serializes the normalized authored source — not the runtime, and not the compiled prompt. So:

• For branching / ensemble / scene-sweep, phases are authored directly → the export already looks almost exactly like the runtime (minus the three engine-added keys).
• For mix-arc, the export carries beats[]; the runtime phases[] are derived by toRuntime.
• For guided-arc, the export is phases[] + scene; the runtime is a mix-arc object via toMixArc (a larger transform).
• The system prompt is never in the export — it's generated at play time by compile().

To see input→output for any scenario, run its source through type.toRuntime() (and type.compile() for the prompt). Both are pure functions on the exported object.

Lessons worth carrying into the production engine

Independent of our exact field names, these are the design decisions that made one engine hold seven interaction types. Offered as starting points, not requirements.

  • One canonical runtime shape. A scenario is a phases[] ladder. Every authoring format normalizes into it; the engine knows only it.
  • The app owns advancement; the model owns voice. Turn caps, tier recording, transitions, and the next locked entry are app logic. The model returns dialogue + a tier — it never drives control flow.
  • Separate data from prompt. toRuntime → JSON the engine drives; compile → a prompt string the model reads. A field earns a place in the JSON only if the engine or a surface reads it.
  • Tier-routed transitions are the branching primitive. transitions[{ onTier, next, set }] covers "record how it went, write state, pick the next rung" — enough for real divergence or deliberate convergence.
  • One optional surface hook, not per-type engine branches. A phase opts a custom renderer in via kind + a self-guarding hook (scene-sweep's perception canvas). No hook, no surface code runs — conversational types stay untouched.
  • Budget for a normalize/migration seam from day one. It's what lets authored content survive schema change — and what makes an old export still play. Retrofitting it later is painful.
  • Reserve the "recipe" adapter for genuine special-cases. Funneling a rich type through another's model is lossy; let branching/ensemble/scene-sweep own their runtime.
