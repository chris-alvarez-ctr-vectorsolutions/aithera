Build & Authoring Specification

A technical view of the scenario flow: what each phase does, what must be authored, what is generated at runtime, and the templates and schemas we need to build once so scenarios can be produced at scale. Companion to the annotated Figma flow.

1

Flow anatomy

The simulator is a single learning object (LO) with a defined entry and exit. Internally it runs three phases: a Scenario Context setup, a repeating Practice ⇄ Learn loop, and a Debrief. Every screen in the flow is one of two kinds — and that distinction is the organizing principle of this whole document.

Authored — written by a content author, fixed at design time Generated — produced by the model at runtime Generated within authored guardrails

The key insight for planning: nothing pink is free. Every generated moment depends on authored inputs — a character card, a rubric, a guardrail set. The authoring work doesn’t disappear when AI produces the words; it moves upstream into structured configuration.

2

Phase — Scenario Context

2

Orient, prime, and gate

The learner sees the scenario title, absorbs the situation in one of three formats, then must produce a sufficient written reflection before practice unlocks. This is the only phase with branching — and the branches are a content format choice, not a narrative fork.

Authored per scenario

Title & framing copyScenario name plus 1–2 sentences setting learner expectations (“Kendra’s room”).
Context content × up to 3 formatsThe same situation expressed as: nothing (skip), a video sequence (asset + captions), and a readable story (rich text with highlight anchors). Each format is optional per scenario, but the story format is the cheapest baseline and should be considered required.
Reflection promptThe open question the learner must answer before advancing.
Sufficiency rubric2–4 plain-language criteria defining what counts as a “sufficient” reflection. This is the gate — it must be authored, not implied.

Generated at runtime

Reflection feedbackModel evaluates the learner’s reflection against the authored rubric and either coaches a retry or confirms readiness to advance.
Advance decisionThe pass/retry judgment itself is a model call constrained by the rubric — engineering owns making this deterministic enough to trust (structured output, threshold logic).

Schema — context block (per scenario)

// scenario.context
{
  "framing": { "title": "Kendra's Room", "expectation": "You'll practice a hard conversation with…" },
  "formats": ["none", "video", "story"],
  "video": { "src": "…", "captions": "…" },
  "story": { "body": "richtext", "highlights": [{ "anchor": "…", "note": "…" }] },
  "reflection": {
    "prompt": "What would you want to understand before responding?",
    "rubric": ["names a specific concern", "avoids judgment language"],
    "retryCoaching": "tone + hint guidance for insufficient responses"
  }
}
Flagged build task (from board note): the format toggle currently appears inside the Scenario Context flow. Per Chris’s annotation, it should be removed here and introduced only once the learner begins practicing — the context format is chosen once, up front, not toggled mid-setup.
→Ties to Practice: the sufficiency gate is the phase transition. Nothing from the reflection needs to carry forward mechanically, but passing it should be logged as the learner’s first proficiency signal in this LO.
3

Phase — The Practice ⇄ Learn loop

3

Beats: act in scene, step out for coaching

The core of the experience is a sequence of authored beats (~4 in the reference build). Each beat runs the same state machine: narration advances the scene → the character responds once → the flow drops to the coach layer for feedback and a nudge → a CTA returns the learner to the scene. The loop is the unit of authoring and the unit of engineering.

Authored per scenario

Character card (once per scenario)Who the simulated character is: voice, backstory, what they know, emotional state per beat, and boundaries (what they never reveal or do). This is the single most leverage-heavy authoring artifact — every generated character line depends on it.
Beat sequenceOrdered list of beats. Per beat: narration copy (scene direction shown to the learner), the character’s objective for that beat (“deflects with humor; softens if learner shows empathy”), and the beat’s learning intent.
Coach rubric per beatWhat good looks like for the learner’s response at this moment — the criteria the coach feedback is generated against.
Response promptsThe authored nudge in the Learn lane (“What do you want to say next?”, “Who could you connect her to?”). These steer without scripting.
CTA copy & advance conditionsButton language and the rule for when a beat is complete.

Generated at runtime

Simulated character response (1× per beat)Single-shot, not open chat — the character responds once to the learner’s move, constrained by the character card and the beat objective. This constraint is what keeps the scenario authorable and predictable.
Coach feedback (per beat)Generated against the beat’s rubric, in the coach’s configured voice and shape (see §5). Two appearances per beat in the reference flow: immediate feedback, then a CTA-bearing wrap.

Schema — character card + beat object

// character.card (authored once per scenario)
{
  "name": "Kendra", "relationship": "resident / peer",
  "voice": "guarded, dry humor, short sentences",
  "backstory": "…",
  "knows": ["facts the character can reference"],
  "boundaries": ["never volunteers X unprompted", "de-escalates if learner is hostile"]
}

// scenario.beats[n]
{
  "id": "beat-2",
  "narration": "Back in your dorm, you notice…",
  "characterObjective": "deflect, then open up if learner names the feeling",
  "response": { "mode": "single-turn", "maxLength": "short" },
  "coach": {
    "rubric": ["acknowledged emotion", "asked an open question"],
    "responsePrompt": "Who could you connect her to?"
  },
  "advance": { "cta": "Keep practicing", "on": "continue" }
}
→Ties to Debrief: the full beat-by-beat transcript plus each beat’s rubric results are the debrief’s input. The loop must persist a structured record (learner move, character response, rubric evaluation) — not just chat text — or the debrief has nothing reliable to analyze.
4

Phase — Debrief & close

4

Analyze, summarize, hand off

After the final beat, the coach signals a mode shift (“Analyzing…” animation), then delivers the structured wrap-up: overall feedback, strengths, growth areas, and a closing that exits to the next LO. This is where the scenario produces its proficiency signal — so it is the most guardrail-dense phase.

Authored per scenario

Competency frameThe 3–5 named skills this scenario develops (e.g., empathy, open questioning, referral). Strengths and growth areas are generated only within this frame — the author decides what the scenario measures.
Strengths / growth guardrailsConstraints on the generated summaries: evidence must quote the learner’s own moves, max 3 items each, growth areas framed as next steps, prohibited framings.
Closing templateScaffolded closing message with generated slots, plus the exit CTA that links to the next LO.

Generated at runtime

Overall coach feedbackSynthesis of the full transcript against all beat rubrics.
Strengths & growth areasEvidence-grounded, competency-framed, guardrail-bounded. Rendered as structured cards, so this call must return typed JSON — not prose.
Coach closingPersonalized send-off filled into the authored template.

Schema — debrief block

// scenario.debrief
{
  "competencies": ["empathy", "open questioning", "referral to support"],
  "strengths": { "max": 3, "guardrails": ["cite learner's actual words"] },
  "growthAreas": { "max": 3, "guardrails": ["frame as a next step", "tie to a competency"] },
  "closing": { "template": "scaffold with {generated} slots", "cta": "Continue" },
  "exit": { "nextLO": "lo-ref", "emitSignal": "proficiency-record" }
}
→Ties to the LO sequence: the exit emits a structured proficiency record (competencies × evidence), which is what makes this scenario a composable LO rather than a dead-end activity — and what feeds the broader provable-proficiency signal downstream.
5

Cross-cutting: built once, reused everywhere

Several artifacts sit outside any single scenario. These are the platform layer — they get built and tuned once, and every scenario inherits them. This is where scale actually comes from.

Configuration (authored once, org-level)

Coach configThe coach’s persona, tone, feedback shape (e.g., “two sentences + one question”), coaching framework, and safety rules. One coach voice across all scenarios; overridable per scenario only if we ever need it.
Prompt templatesThe assembly recipes that combine character card + beat + transcript into each model call: character-response template, coach-feedback template, reflection-gate template, debrief template. Four templates cover every generated moment in the flow.

Engineering (built once)

Scenario player / state machineDrives the phase and lane transitions: context branch → reflection gate → beat loop → debrief → exit. Reads any conforming scenario JSON.
Typed message schema + worker proxyExtends the established pattern (typed JSON messages, Cloudflare Worker proxy for model calls) already proven in the conversation-practice module. All generated moments return structured output validated against the schema.
Transcript & signal storePersists the structured beat record and emits the exit proficiency signal.
Authoring validationSchema validation + a lint pass (every beat has a rubric, every rubric has ≤4 criteria, character card has boundaries) so authored scenarios fail fast, not in front of a learner.

Open decisions before build

Three calls worth making early because they shape the schema: (1) rubric evaluation trust — whether the reflection gate and beat rubrics use pure model judgment, structured scoring, or a hybrid with retry thresholds; (2) beat advancement — whether a beat can require a minimum rubric result before its CTA activates, or advancement is always learner-driven; and (3) the proficiency record shape — what the exit signal contains, since that contract is what makes these scenarios legible to everything downstream of them.
