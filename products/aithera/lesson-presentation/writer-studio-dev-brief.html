1

What it is

The one-sentence framing

Designers author meaning in plain-language fields; the tool authors the prompt.

The Writer Studio is the authoring tool behind the Scenario Simulator. A content designer fills structured, plain-language fields — never raw prompt text — and a per-type compiler assembles the LLM system prompt around locked, safety-critical sections the designer can see but not break. The same draft data drives the learner-facing live pages.

2

How it works — the flow

Two ways in — the structured editor, or the “Start from scratch” wizard (a short brief + interview that generates a complete first-draft scenario the designer then edits). Both produce the same draft object.

1Pick a scenario typeaction-practice, guided-arc, ensemble, etc.
2Author the draftfill structured fields, or run the wizard — each field maps to a data-path in the draft
3Compiletype.compile(draft) → the LLM system prompt
4Playtestrun the draft against the live model — no publish needed
5Publish → livethe matching *-live.html page reads the published draft and runs the scenario
The architectural idea worth saying out loud

The app shell is type-agnostic — it never knows which pedagogy it's editing.

The shell talks only to a type's public surface. Adding a new scenario type is adding a module + one include line — the shell doesn't change. (There are zero if (type.id === …) branches in the shell.)

What a “type” must provide

The contract the shell relies on: id / label / icon / blurb, a shipped DEFAULT exemplar, the locked ENGINE_SECTIONS, validate/normalize/merge helpers, compile(), the editor sections + renderFields, lints(), a previewUrl, and optionally a wizard spec and a playtest block.

4

What it outputs

Three things, all derived from the one draft object.

  1. The compiled system prompt — the primary artifact. type.compile(draft) returns a prompt string or an ordered [{role, label, text}] set. Designer text is interpolated into locked, non-editable safety sections (crisis floors, grounding, the output contract) — visible in the Guardrails tab, un-editable by design.
  2. A published scenario — the draft JSON written to a “published” slot that the matching *-live.html page reads to run the actual learner experience.
  3. A saved library — named drafts the designer can reload.

Supporting views in the inspector: the live Guardrails, a Playtest transcript, Lints (authoring warnings), and the Say/Do Split preview of how a learner's move is parsed into say-vs-do beats.

Framing for devs

The durable output is structured scenario data + a deterministic compiler. The prompt is derived, not hand-written — so prompts stay consistent and the safety sections can't be edited away.

  Prototype scaffolding — not the product

Prototype-specific features

Everything below exists because this is a vanilla-JS prototype — no backend, no framework, no build step. These are the seams a real product replaces. Call them out early so nobody mistakes scaffolding for architecture.

  The Cloudflare Worker — the LLM proxy

A thin Cloudflare Worker proxies the browser's model calls. The prototype has no server, so the wizard and Playtest POST straight to it.

  • Default URL: https://aithera-action-proxy.vector-aithera.workers.dev — overridable per-browser, stored in localStorage (aithera.writerStudio.workerUrl), shared across every type and the Playtest.
  • The call: POST JSON { model, max_tokens, system, messages:[{role:'user',content}] }; response parsed Anthropic-style (data.content[].text, stop_reason).
  • Model: claude-opus-4-8, pinned in the engine (one place).
  • Token ceiling: each step requests its own max_tokens, clamped to 2000 (the Worker caps there). Truncated mid-JSON → one “be terser” retry; malformed JSON → one “JSON-only” retry.
Why it matters for the review: the call site is already centralized. Production swaps this Worker for a server-side, authenticated LLM call behind the same interface — no rewrite of the types or the shell.
  Persistence — localStorage
  • Draft, published, and library slots are browser localStorage, namespaced per type (aithera.writerStudio.draft.<id>.v1, …published.<id>.v1, …library.<id>.v1).
  • Publish → live is a same-browser handoff: publishing writes a localStorage slot the live page reads on the same machine. No shared/remote publish yet.
  • ~5 MB origin cap; writes are quota-guarded (an embedded photo can blow the budget → friendly “image too large” message, not a silent failure).
  • The seam: all persistence goes through one factory (makeStore). Swap localStorage for an API behind the same { loadPublished, publish, saveToLibrary … } surface and nothing else changes.
  No auth · No build step · Review tooling
  • No auth — the studio and live pages are open, no per-user/org scoping. Production gates the pages and scopes the store keys.
  • No build step — plain <script>/<link> tags with hand-managed ?v=N cache-busting. Shared files need ?v= bumped everywhere (plus the service-worker VERSION) or browsers serve stale modules.
  • Review-only tooling — the bottom-center toolbox dock and its 🗺 Flow Map are review/handoff tools, not part of the product. The toolbox.js include is stripped for dev handoff.
