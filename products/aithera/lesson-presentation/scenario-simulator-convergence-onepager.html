The change

Two moves: freeze the old world, then collapse the players

First we captured a frozen, self-contained snapshot — archive/2026-08-04/ plus the git tag archive/pre-option-b-2026-08-04 — so every page demoed last week still renders its exact behavior and stays linkable forever.

Then the real change: one learner page, scenario-live.html, routed by ?type=, sitting on one shared, DOM-free ladder engine, js/sim-player.js. The engine was lifted verbatim out of the old per-type pages — so this was a re-wiring, not a rewrite, and the learner sees no difference.

The new unit

A scenario "type" is now one module — authored and run from the same definition

The unit of the system used to be the page. It's now the type module. Each js/scenario-types/*.js exports one contract read from two directions: the player reads toRuntime / compile / fill; the Studio reads sections / lints / wizard / previewUrl. And previewUrl now points the Studio's preview button straight at scenario-live.html?type=<id>.

So authoring and playback are two faces of one definition — they cannot drift. Five ladder-shaped types route through the single player (guided-arc rides in as a mix-arc "recipe" via toMixArc); teach-back and the hazmat observe type keep their own pages by design, because they aren't ladder-shaped.

Extensibility — the proof

How a new interaction surface plugs in: scene-sweep is the worked example

Your instinct is right — scene-sweep needed something the ladder had no concept of: a full-bleed, tappable photo. The important part is what it didn't do. It did not fork the engine. It plugged in along three seams:

Is the engine agnostic to this? Yes — where it matters. The ladder logic is DOM-free; it grades turns and routes phases and knows nothing about photos, pins, or canvases. A new interaction surface never reaches into that loop. At most it adds one more guarded hook like coverageBlock. The place a new modality actually lands is the renderer / host page — not the engine.

The hard question

If the content team wants a 3D scene or Google Maps embed

Two separate questions hide in that ask: does it fit the pedagogy, and what's the dev lift. Take them in order.

Fit test Can the interaction reduce to a gradeable signal?

The engine grades by scoring the learner's turn against a phase's exit-criteria into a tier. A custom surface fits when its interaction produces a signal you can score. Maps: "find the nearest exit," "plot the muster route" → a clicked place / dropped marker / drawn route becomes the turn. 3D: "walk the floor, tag three lockout points" → selections become the turn. That's the exact shape scene-sweep already runs: marks → a spotted list → judged. If the objective is free exploration with nothing to assess, it isn't a simulator interaction — don't force it onto this engine.

The authoring flow is nearly free. In Writer Studio it looks like every other type: the author fills the new type's phase sections and places targets on the surface — the map/3D equivalent of "drop the hotspot on the photo," using the same shared geometry — the wizard scaffolds a starting scenario, and "Learner preview" opens scenario-live.html?type=<new>. That half is cheap precisely because the Studio is already type-agnostic.

Caveat 1 External embeds vs. the prototype rule

Google Maps needs a keyed SDK and a live network; a real 3D scene wants a library like three.js. Our prototype contract is the opposite: vanilla JS, no build step, no external libraries, must run from a double-clicked file://. So a prototype can only simulate these — and note that "a static map tile with tappable overlays" is literally scene-sweep again. The genuine embed is a production dev-team lift the mock environment can't host. Worth setting that expectation with the content team up front.

Caveat 2 The host page isn't a plugin bus yet

Today scenario-live.html hosts scene-sweep through ~10 hand-placed IS_SWEEP branches, not a registry. One custom surface is fine. Before a second, promote that into a small surface registry keyed by phase kind so the page stops accreting per-modality branches. It's the natural next refactor — the hooks are already named for it (sceneNode / updateHud / reposition / enterMarking) — it just hasn't been done.

Why bother

What the surface registry would buy

It turns "edit the player for every new surface" into "drop in a module and register it."

// today — the surface is named directly, guarded at ~10 call sites
if (IS_SWEEP) PERCEPTION.updateRail();
if (IS_SWEEP) { PERCEPTION.enterMarking(); return; }

// after — the page calls one interface; new surfaces just register
const surface = Surfaces.forPhase(phase);   // by phase.kind; null = conversational
surface?.onRender(stageInner);
Surfaces.register({ kind: 'map', install: SimMap.install });   // page unchanged
  • New surfaces become additive. A new interaction type is one folder — type module + surface module + shared geometry — registered in two places, with zero edits to the shared player. That's the same property the authoring side already has via AitheraStudio.register; this makes all three registries symmetric — author types, runtime types, render surfaces.
  • The contract becomes explicit. "What a surface must provide" is implicit today — smeared across ~10 call sites and one ad-hoc install({…}) argument list. A registry forces it into a named, documentable interface.
  • "Others stay byte-identical" stops being vigilance. Today that guarantee is held by hand — every branch guarded on IS_SWEEP. A registry makes it structural: no surface registered for a phase → no surface code runs, by construction.
  • Smaller blast radius. Each surface's logic sits behind a uniform boundary, so a change to one surface can't perturb another or the conversational path.
  • The real unlock — per-phase surfaces. IS_SWEEP is effectively whole-run today. Resolving the surface per phase by kind lets one ladder mix a spot phase and a map phase — a new authoring capability, not just cleaner code.

Timing: don't build it speculatively from scene-sweep alone — one example over-fits the abstraction. Extract the registry while building modality #2, factoring the interface from two concrete surfaces. It's also orthogonal to the file:// dependency wall — this cleans up the host page's internals, not what a surface may load.

Bottom line

  • Sustainable for one family: "the learner produces gradeable signals on a custom surface." scene-sweep proved the seam; the next surface is ~2–3 new self-contained files plus, at most, one tiny engine hook — and the authoring side is close to free.
  • The friction isn't the engine. The ladder core is DOM-free and stays untouched. New modalities land in the renderer, not the grading loop.
  • Two things to plan for before modality #2: external-dependency embeds (Maps/3D) collide with the file:// prototype rule — prototypes can only simulate them; and the host page needs a real surface registry so it doesn't keep growing per-modality branches.
