The static prompt layer: what each side should take from the other

Both engines compile authored content into a model prompt, and both wrap it in a fixed scaffold nobody authors — the turn budget, the non-answer rule, the safety floor, the close. That scaffold has never been compared. This page diffs it line by line and sorts every difference into three piles: the UX POC adopts, the dev POC adopts, and neither — it is how each engine talks to its model, and harmonizing it would be a rewrite for nothing.

What "static" means here scope

Everything an author never writes and never sees. In the dev POC that is two prompt templates (scenario-coach, scenario-scene) plus the per-turn directive blocks generated in prompt_v3.py and the edge-case rules in assessment.py. In the UX POC it is the fixed prose each type module's compile() emits around the authored fields, the [SYSTEM STATE] line built in js/sim-player.js, and the shared SimCore.nonAnswerPolicy. Authored content — teaching points, canon, calibration tiers, locked hand-offs — is out of scope; that comparison is the alignment notes.

One caveat that shapes every "the dev POC doesn't have it" below verify

What "Langfuse-managed" means. Langfuse is an open-source LLM observability platform, and one of the things it does is prompt management: prompt templates are stored in Langfuse under a name, with versions and labels, and the app fetches them at runtime — get_prompt("scenario-coach") — instead of reading a string out of its own source. The point of that is a non-engineer can edit the prompt and ship a new version without a code change or a deploy. The dev POC uses it for both halves: the two prompt templates, and the per-turn traces, ratings and reviewer notes.

Why that makes this page provisional. The templates in the repo are fallbacks, not necessarily what runs. get_prompt(name, type="text", fallback=…) resolves in one of three states, and only the third breaks the diff: no Langfuse credentials configured → the repo copy runs verbatim; credentials set but the prompt never authored in Langfuse → the repo copy still runs, via the fallback; credentials set and the prompt authored → the Langfuse version runs and the repo copy is dead text.

So this is one question, not an assumption. Nothing here says the text has drifted — it says it is unverifiable from the repo alone, in either direction. "Are scenario-coach and scenario-scene authored in Langfuse, and can the live versions be shared?" settles every finding on this page at once. It is also ask B6 below, and the cheapest thing on it.

How to read this

Sorting by cost matters more than sorting by merit — most of this page is prompt text, and prompt text does not need a meeting.

Pile A · The UX POC adopts

Seven things the dev POC's scaffold does that the UX POC's doesn't

Six are a string edit across the four type modules and sim-player.js. None needs the dev POC's agreement, and none touches the format.

A1 Never affirm a statement that contradicts the situation prompt text

The dev POC
"If the learner gets a fact of the scenario wrong — who someone is, what happened, when — correct it plainly before you build on anything else they said, then carry on warmly. 'Exactly right' about a wrong fact teaches the wrong thing and undoes the credibility of everything else you say. Correct the fact, not the person, and do not make more of it than it needs."— _DEFAULT_COACH_TEMPLATE, app/services/langfuse.py
The UX POC
Nothing equivalent, in any of the seven composed prompts. The nearest thing is per-tier calibration guidance, which grades the quality of the judgment and says nothing about whether the learner's premise was factually true. A learner who says "well, Dana apologized afterwards" — he didn't — gets built on.
Why it's worth taking
It is the one rule here that protects the authored canon from the coach rather than from the learner. The UX POC spends a lot of prompt on stopping the model inventing facts; this stops it ratifying an invented one, which is the same failure arriving from the other direction and is invisible in review because the coach's reply reads warm and competent.
Where it goes
The shared coach preamble — the same block that carries VOICE and THE RHYTHM in mix-arc.js, v4-universal.js, branching-arc.js, ensemble-arc.js.

A2 Coach-level no-invention, including the organization-policy clause closes a regression

The dev POC
"Never invent facts… Do not add incidents, names, dates, numbers, policies, or legal standards that are not in it. Where the answer would be a specific organization's own policy or procedure, say what is true generally and send the learner to their own organization's policy; never state what it says."— _DEFAULT_COACH_TEMPLATE
The dev POC's own comment names the hazard: a coach asked "what does the policy say?" answering with a policy it made up.
The UX POC — and the regression
The UX POC's native types carry a canon no-invention line, but it is compiled as part of the LOCKED SCENARIO CANON block — "NEVER invent new incidents, names, injuries, or biography beyond it." The v4 route has no canon block. Grep the four v4 scope dumps for invent and you get exactly two hits: never invent other tier labels, and never invent footage that isn't there. There is no general no-invention rule on the v4 route at all. The scope split dropped it, and nothing caught that because the natives still had it.
The half neither route ever had
The organization-policy clause. Every one of the UX POC's compliance scenarios is exactly the kind where a learner asks a policy question, and "say what is true generally, send them to their own policy" is the correct answer in all of them.

A3 Warn one turn ahead, and say what the last turn may not do prompt text

The dev POC
Every turn carries a # Turns block. Mid-budget: "This is the learner's turn 2 of 3 in this stage; they will get at least one more after this reply." On the last one allowed: "Statements only: land the point and hand off. Do NOT ask a question and do NOT open anything new." In a scene, one line more: "Bring the moment to rest — someone goes quiet, walks away, accepts what was offered — rather than raising something new." The rule behind it is CML §12: a learner must never be left facing a question they will not be allowed to answer.
The UX POC
The UX POC's state line reports Learner turns used: 2/3 and then, only once the cap is consumed, THE CAP IS REACHED — you MUST set "action":"teach". Identical at the boundary — but the model writes its penultimate turn with no idea it is the penultimate turn, so it can open a thread it will never be allowed to close. The forced teach then has to abandon it.
Cost
Two clauses in arcStateBlock(), js/sim-player.js:186. The count is already there; only the phrasing changes.

A4 The bare-acknowledgement short-circuit engine (small)

The dev POC
A learner input that is exactly yes / y / yeah / yep / yup / no / n / nope / nah after trimming and stripping trailing punctuation never reaches the model. The engine appends the learner's own line plus a fixed prod — "Walk me through your thinking there." — marks the exchange budget_inert, and returns. An anti-loop guard sends the second consecutive ack to the model normally. "yes but", "no idea" and "yesterday" all fail the exact match by design.
The UX POC
A bare "yes" costs a model call and then a coin flip: graded as a thin attempt (turn spent) or called a redirect (turn refunded). On a deterministically detectable input. The UX POC already ships this exact shape elsewhere — REFLECTION_STAY_CAP is the same idea, engine-owned and bounded, applied to the warm-up.
Cost
One predicate and one early return in the send path, plus the anti-loop guard. Cheaper than the model call it replaces.

A5 Guardrails on "Step out to AI coach" prompt text, then engine

What the UX POC already has
The affordance itself, and it is good: stepOut() pauses the scene, flips to the coach, and the turn is budget-inert by construction — inPhaseWorld is false, so the counter never ticks (scenario-live.html:3374). The dev POC's equivalent is help_turns, and both sides independently decided a sidebar must not cost scene turns.
What the UX POC lacks — the framing
manualTimeout is invisible to the prompt layer. Neither sim-player.js nor the scope module ever reads it, so a step-out turn gets the ordinary prompt with the mode flipped and no sidebar directive at all. The dev POC has one:
"Answer as their coach: orient them, clarify what is being asked, or nudge their thinking using only what the scene has already established. Do NOT solve the exercise, script their next line, or reveal or preview what the strongest response would be — the practice is still theirs to do."— _help_turn_directive, prompt_v3.py
Nothing in the UX POC's prompt tells a stepped-out coach not to hand over the answer, mid-practice.
What the UX POC lacks — the bound
The dev POC's is capped (default 2) and, once spent, the engine injects a locked line with no model call: "Sorry, I've helped all I can for now. We'll talk more after your practice." The UX POC's is uncapped — a learner can step out on every move of a scene, forever, for free.
Where the UX POC is already fine
Leakage, on the v4 route only. systemFor keys off the rung rather than the mode, so a step-out inside a scene rung stays in the scene scope, which never sees teaching points or the ideal response. On the native monolith types it sees everything — which is exactly why the directive matters more there.

A6 The three-section close prompt text

The dev POC
Three labelled blocks, every time — [[section:RECAP]], [[section:STRENGTHS]], [[section:GROWTH AREAS]] — with the label discipline made structural by an assistant prefill rather than instructed. The dev POC's reason is recorded: letting the model choose its own sections produced closes with no personal feedback at all, observed on two scenarios.
The rules inside it are the real prize
"if they already did the thing you are about to suggest, it is not a growth area — it belongs in STRENGTHS, quoted as theirs — and never suggest their own words back to them as the improvement; that reads as though nobody was listening. A learner who did well gets a short, honest 'little to add here' plus at most one genuine refinement — never a manufactured gap to fill the section."— _closing_body, prompt_v3.py
The UX POC
On the v4 route, one sentence: "a short, personal closing recap … name what the learner actually did well across the beats and the one thing to carry forward. Keep it to a few sentences." branching-arc has a fuller report block with recap/strengths/growth. The v4 route is the one that ships, and it is the thin one.
Note
Take the rules, not the [[section:]] markers — the UX POC's close is a JSON report object, so the structure is already enforced by the schema. This is A6 shading into C1: same intent, different mechanism, and the UX POC's is fine.

A7 Four small directives prompt text

Driver-input protection
"The learner's latest message may be a UI tap such as 'show feedback' rather than genuine input — do not respond to its literal wording and do not defer; deliver this turn's content now regardless." The UX POC generates app-owned advances the same way and have no such line.
One question per reply
"ask at most ONE question per reply — never stack two questions in one reply, never a second question bubble in the same reply, and never answer your own question. Ask it, then stop and wait." The UX POC says "ONE short probing follow-up," which covers the count but not the stacking and not the self-answering.
Echo-prevention by quotation
Before the app appends a locked line, the dev POC quotes it verbatim into the prompt with "do NOT repeat, duplicate, or paraphrase their content." The UX POC lists every locked hand-off up front and say never repeat an app-owned bubble — good for the arc, weaker for the line landing in the next 200ms.
Zero-turn units
A unit with a budget of 0 is told "This stage takes no learner input… Statements only. Do NOT ask a question." The UX POC's caps floor at 1 (Math.max(1, p.maxTurns || 3)), so it cannot express a delivery-only beat at all — the model is always told it has a turn coming that the app will not give it.
Pile B · The dev POC adopts

Six things the UX POC's scaffold does that the dev POC's doesn't

Four are a paste into a template the dev POC already owns. One is a process change. Only B2 has a real argument attached, and it is winnable in a narrower form than the one already on the agenda.

B1a An unconditional character conduct floor lead with this

The ask
Paste a fixed floor into _DEFAULT_SCENE_TEMPLATE, applying to every character in every scenario, over and above whatever the author wrote: never abusive, threatening beyond what the scenario itself establishes, sexually explicit, or demeaning; keep every moment recoverable, so however badly a beat is played a better next move still lands; characters stay human and specific, never a caricature or a stereotype of any group; if the learner drags a character toward any of those lines, de-escalate in-world and keep the scene playable; never address the learner by name.
Evidence there is nothing
Grepped app/ for the whole vocabulary — abusive, sexually explicit, slur, de-escalate, recoverable, caricature, minors, crisis, self-harm. The only hits are behavior.guardrails, the per-character authored list. A character stays in bounds exactly as far as an author remembered to write a bound for them.
Why this one is easy to say yes to
The dev POC's own content already agrees with it. The bullying deck's slide 5 hand-authors a GUARDRAIL line per character — "Never abusive; de-escalates in proportion to feeling heard" for Ms. Reyes, "never a caricature of a 'bad kid'" for Bianca. Two authors wrote by hand, for one scenario, what a template guarantees for all of them. And it costs no schema change — it is the same class of move as the three things it already promoted out of authored content into the template (the universal coaching rules, the no-invention rule, the fixed-arc causality rule), for exactly the same stated reason: anything true of every scenario is prompt engineering.

B1b The three flag-gated safety floors needs proposal #1

The ask
Three more locked blocks, each compiled only when the scenario declares the matching flag: LEARNER SAFETY (a learner disclosing real danger as themselves → drop the exercise, warmth and zero assessment, real support, 988 for self-harm), THREAT-CONTENT FLOOR, MINOR-SAFEGUARDING FLOOR. The flags are elevated_stakes, threat_content, involves_minors — the same three the extensions envelope exists to carry.
What this adds to the existing proposal
The #1 card argues the mechanism and asserts the consequence: "loads with no crisis floor and no trace one ever existed." That was an inference from the schema. It is now what the templates say — there is no crisis handling anywhere in the dev POC's prompt layer, flagged or not, so the flag has nothing to switch on even if it survives the loader. Raise B1a first and B1b becomes the obvious follow-on rather than a separate fight.
Sequencing
B1a is a paste and needs no decision from anyone. B1b needs the envelope. A no on the envelope must not take the conduct floor down with it — same discipline the talking points already applies to splitting ask 01 from ask 02.

B2 Refund the clarifying question — and cap the refunds both sides change

Don't re-run the old argument
The dev-conversation card frames this as the spec deciding wrongly. It's stronger, and more honest, to note the dev POC built this and deleted it:
"an edge case no longer exempts a turn from advancement or from a stage's turn budget at all — 'a wasted turn is a spent turn'. Both of the mechanisms this used to interact with were deleted outright, not narrowed."— app/services/assessment.py
And the deletion was right for its target. A live run spent 8 learner turns against a stage authoring max_turns=2 because a disengaged learner's filler read as a refusal and exempted every turn. The UX POC's policy already agrees on that case — a second "I don't know" in the same unit stops being free and is graded as the thin attempt it is.
The narrow ask
Only the other case, the one §7.2.4 settles the other way: "a clarifying question is just a turn." On the 2-turn budgets the POC content actually uses, a learner who asks "wait, am I the supervisor here?" has spent half their practice on a question. Refund that; keep spending disengagement.
Concede the UX POC's own half
The UX POC's refund is model-enforced, not engine-enforced. action:"redirect" rebates unconditionally and nothing bounds how many times per unit — the "second deflection is no longer free" rule lives only in the prompt, so a model that keeps calling non-answers redirects loops exactly the way the dev POC's renee run did. The UX POC has the bound on the warm-up (REFLECTION_STAY_CAP) and not in the phases.
The synthesis neither side ships
Refund the non-answer, but cap the refunds per unit — one or two, engine-side. That answers the dev POC's objection (a disengaged learner cannot farm free turns) and the UX POC's (a clarifying question doesn't cost practice) with one mechanism, and it is a change on both sides rather than an ask on one. Worth noting the dev POC already runs two budget-inert paths — the bare ack and the help channel — so the principle isn't foreign; the disagreement is only over which cases qualify.

B3 An enumerated banned-phrase list the dev POC asked for it

Already on the dev POC's books, apparently unlanded
AI Quality Review v2 — 248 rated turns, 183 reviewer notes — recommendation #10: "Avoid openers like 'You're right to feel that way,' 'It's brave to acknowledge,' or empty praise for trivial actions." As far as the repo fallback shows, the coach template never got it. What it did get is the length half ("keep every reply SHORT… never a wall of text") and "you are not a quiz machine." The sycophancy half is missing, and the reviewer notes behind it are blunt: "we're overstating our validation of their response again."
The UX POC
An enumerated ban — "I appreciate you being straight with me", "I hear you", "that's valid", "sit with that", "here's the thing", "let's unpack", "lean into", "hold space", "a lot of people land right where you are", "great question", "does that resonate", "I want to gently push" — plus two clauses that do the real work: "never use these or anything that pattern-matches them", and "vary how you open bubbles; don't start consecutive bubbles the same way."
Why the form matters, not just the content
An enumerated ban is checkable in review; "avoid empty praise" is not. A reviewer can grep a transcript for the list. That is also why it survives a model swap — the dev POC's traces show the failure across Llama, Gemma and Haiku alike, which is a prompt problem, not a model problem.

B4 Role confusion as a named non-answer case prompt text

The gap
"wait, am I the supervisor?", "who is that again?", "is this graded?" — a learner who has lost the thread of who they are. Under detect_edge_case this matches no cue list, classifies as none, is tier-assessed as a genuine attempt, and spends a turn. It is the single most common non-answer in a scenario that opens with a role assignment, and it is the one the dev POC's taxonomy has no name for.
The UX POC
Named as case 1 of three: "ANSWER it plainly and briefly in your own voice, then re-pose the SAME prompt you just asked. Never treat the question itself as their decision, and never grade a phase on it."
Independent of B2
Worth saying explicitly in the meeting: this is a grading ask, not a budget ask. Even if the dev POC never refunds the turn, the input should not be read as the learner's answer and should not select a tier. Splitting it from B2 is what lets it land on its own.

B5 A model-side non-answer taxonomy behind the server detector prompt text

Not a replacement
The dev POC's server-side detect_edge_case is the half the UX POC doesn't have, and it is worth keeping: deterministic, free, traceable, and it fires before a model call. The ask is to put something behind it, because it is substring matching over two fixed cue lists — an empty string is off_topic, "disregard" fires inside an innocent sentence, and prompt injection is caught only when phrased from the list.
What the UX POC adds
The residue, judged in the model: the three-case taxonomy, the scene clause ("the moment passes WITHOUT the learner having acted — never narrate them doing something they did not choose"), and the exception that keeps it from over-firing — "a turn that genuinely ATTEMPTS the task and also asks something on the side is a REAL answer… never downgrade a real attempt to a redirect."
The two compose
Detector for the cheap certain cases, model for the rest. That is a better design than either side is running, and it costs the dev POC a paste.

B6 Snapshot the live templates into the repo process

The problem
Half the dev POC's static layer may not be in git, and there is no way to tell from the repo which half. The templates there are labelled fallbacks, so whether they ran depends on a Langfuse deployment state that the source doesn't record. The consequence is the same either way: nobody can diff the prompt that actually ran against a commit — including the dev POC itself, after the fact. This page had to carry a caveat on every finding for that reason.
Why it gets sharper if B1a lands
A safety floor that lives in a runtime-editable prompt store sits outside code review. That is a different risk profile from the same words in langfuse.py, and it is worth naming while the floor is being agreed rather than after.
What the UX POC does, offered as the pattern
docs/composed-prompts/dump-composed-prompts.js loads the type compilers under Node and writes every composed prompt to a text file that is committed. It is 90 lines, it made this crosswalk possible, and the equivalent in the dev POC is a script that pulls each managed template version at deploy and commits it. Ask: pin or snapshot the live templates on every deploy, and keep any safety floor in code rather than in the store.
Pile C · Neither

Differences that are just how each engine talks to its model

These look like gaps in a side-by-side and are not. Porting any of them is a rewrite with nothing learner-visible at the end, and one of them would actively break something if "reconciled".

C1 Output shape — JSON turns vs. control markers

The difference
The UX POC: one JSON object per turn, turn[] of typed bubbles with kind routing each to the coach sheet or the scene, plus action / tier / complete. The dev POC: streamed prose with [[character:]] / [[phase:]] / [[assessment:]] / [[intent:]] lines stripped before display.
Why neither ports
Each follows from its renderer. The UX POC reveals bubbles one at a time and needs them pre-split and typed; the dev POC streams, and a JSON envelope would block the first token. The semantics are already the same — the dev POC's [[intent:teach|probe|redirect]] is the UX POC's action field almost exactly, down to "the app never advances on a redirect." Same contract, different wire.

C2 One state line vs. per-turn # blocks

The difference
The UX POC appends one [SYSTEM STATE — …] line carrying phase, turns, ladder and session variables. The dev POC appends several small # Turns / # Marker / # What this stage is for blocks, each generated by its own function.
Why neither ports
Same information, different packaging, and each fits its codebase — the dev POC is a Python service with unit-testable pure functions per block, the UX POC is a browser player assembling one string. The only thing worth carrying across the line is content, which is A3.

C3 Contingency — these two rules are opposites on purpose do not reconcile

The dev POC
"The arc is authored: never imply the learner's handling of one moment determined WHAT happens next in the story — their handling only shapes HOW that next moment goes for them." Correct there: advancement is forward-only and server-owned, every budget and requirement is authored, and tiers never participate in routing. The dev POC's comment even names the scenario that forced the rule — WPV's Phase 4 escalation is scripted to follow Phase 3 regardless.
The UX POC
"CONSEQUENCES CARRY FORWARD: how the learner handled an earlier beat is RECORDED and written into the session STATE. Read the [SYSTEM STATE] line and let it shape later beats." Correct in the UX POC: the reported tier selects a transition record, which writes state and names the next phase.
The warning
Each rule is a true statement about the engine that wrote it and false about the other. If these ever get harmonized, one engine starts lying to its learners — either the UX POC promises a fixed arc while branching, or the dev POC implies consequence where there is none. Flag it in the meeting as a known, deliberate divergence so it doesn't get filed as drift.

C4 Already converged — don't re-litigate

Settled
The three-level scale, the phase / practice / debrief model, the split-scope architecture (two conversations in the dev POC; four scopes in the UX POC), locked hand-offs owned by the app, and the anti-giveaway rule in perception beats — the dev POC's "never name an item the learner hasn't found", the UX POC's "nudge toward WHERE to look, never name what's there." That last pair is worth one sentence in the meeting: two teams, no comparing notes, same rule. It is the same signal as the RRRC / OC / CCR structure match.
Sequencing

What to do, in what order

The UX POC — no coordination needed this week

One pass across the four type modules plus sim-player.js lands A1, A2, A3, A6, A7 and A5's directive. All prompt text, all shippable without a meeting, and A2 is a regression fix rather than an improvement — the v4 route currently has no general no-invention rule at all, so it goes first.

Then the two engine items, smallest first: A4 (bare-ack short-circuit), then A5's step-out cap, then the UX POC's half of B2 — the per-unit refund cap that makes the ask credible when it is raised.

The dev POC — the running order for the conversation meeting

Lead with B1a. It is a template paste, it costs no schema change, the dev POC's own decks already hand-author it per character, and it is the same move it has made three times before for the same stated reason. A yes there makes B1b the follow-on to proposal #1 rather than a second argument, and it earns the rest.

Then the three other pastes — B3, B4, B5 — as a group, since none of them needs a decision beyond "sure." B4 in particular should be put as a grading ask, not a budget ask, so it lands independently of B2.

B2 last, and in the narrow form: refund the clarifying question, cap the refunds, and open by conceding that the dev POC's deletion was right for the case it targeted and that the UX POC's own version is unbounded. B6 closes — it is the process ask that makes B1a durable, and it is easiest to agree to once there is a floor worth protecting.
