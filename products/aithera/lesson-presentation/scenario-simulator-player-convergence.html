Scenario Simulator · Option B · Design + Spike

One player, many pedagogies

The authoring side is already universal — one shell drives every scenario type with zero per-type branches. The player side is not: the same “ladder runner” is copy-pasted across seven live pages in three engine generations. This is the plan to give the runtime the same single-shell shape the studio already has — and a working spike that proves the two hardest claims before any broad migration.

1

The asymmetry we’re fixing

Two layers, two very different shapes. The authoring layer is the model to copy; the player layer is the debt to pay down.

Authoring is already a single shell

js/studio-shell.js is fully type-agnostic — grep it for type.id === and you get zero hits. It resolves a type from ?type=, then talks only to the type’s public surface (DEFAULT / normalize / sections / renderFields / compile / lints / previewUrl / playtest / wizard). Adding a pedagogy is adding a type module + an include line; the shell never changes. That is exactly the property we want on the runtime side.

The player is four engines held together by copy-paste

The learner-facing “ladder runner” (runArcEngine, closePhase, applyDeliver, deliverTurn, entryBeatsFor) is duplicated across seven live pages of 2.8k–4.3k lines each. It splits into three engine generations — but they are far closer than their line-counts suggest:

The load-bearing finding. The four tier-ladder pages share a byte-identical runArcEngine / closePhase / applyDeliver / deliverTurn / arcStateBlock. The runner is already one module — it has just never been extracted into a file. Guided Arc is one generation behind it; the marshall-live pages are two behind and are legacy content already superseded by the guided-arc type (whose DEFAULT literally is “Bystander Intervention: The Marshall Scenario”). So “Marshall” as a migration target means the guided-arc type, not the marshall-live page.

The coach-bubble renderer coachNode tells the same story: it appears across 16 pages in three render styles, but the emitted DOM and class vocabulary (coach-msg / coach-avatar / coach-body / coach-bubble, grouping grp-first / grp-last, prompt-lift is-prompt / just-asked) are identical. Six ladder pages already use the good “reconcile” strategy (scroll-preserving, WeakMap-cached); nine use an older full-rebuild; teach-back is a one-off. The component is uniform; only the update strategy differs.

The idea: mix-arc is the general case

Every curated pedagogy is a special case of the composed-beat model. That is not an analogy — it is a schema fact, and it is what lets one runtime serve them all.

A Mix & Match scenario is an ordered list of beats, each carrying one interaction kind (coach-led / roleplay / observe) and its own turn cap. The tier-ladder runner already indexes scenario.phases[] by a per-step world — so a beat is a phase. Guided Arc decomposes into that model cleanly:

Guided Arc → Mix & Match, beat for beat:
  reflection (warm-up)    → reflection (kept 1:1 — non-evaluated)
  phase “The Law” (right answer) → coach-led beat + hasRightAnswer + throughLine
  phase “The Person” (open) → coach-led beat
  the live break-room scene  → roleplay beat (counterpart: Jake)
  SME playbook + resources  → playbook + resources (kept 1:1)

The two schemas already share their entire top level — title, course, framing, learnerRole, establishing, openingImage, intro, voice, reflection, playbook, resources are the same field names. Only phases+scene (guided-arc) vs beats (mix-arc) differ. So the design is:

  • One extracted player-shell — a runtime sibling of studio-shell.js — that boots any type from ?type= and drives the tier-ladder runner with zero per-type branches.
  • A runtime contract each type exposes: type.toMixArc(scenario) (a.k.a. toRuntime) that maps the type’s own schema into the tier-ladder model. mix-arc is the identity; a recipe supplies the mapping. The shell then runs the same compile() + runner path for everyone.
  • One coachNode shared component (the reconcile strategy) + the grouping/prompt-lift passes, driven by the union message contract.
Why this is safe. It is purely additive. The extracted shell is a new page (scenario-live.html) and a new module; the existing per-type live pages keep working untouched. A type joins the shared runtime only when its previewUrl() is flipped to scenario-live.html?type=<id> — one line, one type at a time, each flip proven before the next. The frozen archive (archive/2026-08-04/ + tag archive/pre-option-b-2026-08-04) is the before-picture for every A/B check.

The runtime contract

What the extracted shell reads, so a type can satisfy it without the shell knowing which pedagogy it is running. This is the runtime analogue of the authoring contract in README.writer-studio.md.

SurfaceWhat the runner consumes
Scenariophases[], state[] (session vars), intro{type,video,audio}, establishing, openingImage, title, course, learnerName, characterName, playbook, resources, elevatedStakes
Phase / beatid, label, world (scene|coaching), maxTurns, counterpart, calibration[].tier, transitions[]{onTier,set,next}, debrief.talkItThrough, inputPlaceholder, entry{cta,bridge,bridgesByTier,signpost,prompt,beats[]}; observe adds type+media.segments[]
Model turnturn[], action (continue|teach|redirect), tier, deliver, complete, report, mode, inputTarget; scene-sweep adds spotted
Type objectcompile(), normalize(), fill(), DEFAULT, store.loadPublished(), and new: toMixArc()
Shared modulesSimCore (turn parser/engine/history/callModel), SimContext, SimCoachSheet, SimChatHistory, SceneContext, SimDebrief — already extracted; the orchestration around them is what is not

Everything in rows 1–3 is what toMixArc() has to produce. Because mix-arc’s own normalize() already emits this shape, a recipe’s toMixArc() only has to translate its field names into beats — which is a pure data transform with no runtime coupling.

The spike — what was built and proven

Two new artifacts, both additive, that de-risk the whole track before any page is migrated.

Artifact 1 — guided-arc.toMixArc()

A ~60-line method added to js/scenario-types/guided-arc.js (additive; nothing that consumes Guided Arc today calls it). It maps each Learn phase to a coach-led beat, the terminal scene to a roleplay beat, and carries reflection / playbook / resources / intro / voice across 1:1:

Guided Arc→ Mix & Match beatFidelity
phase.signpost / .promptbeat.entry.signpost / .prompt (verbatim locked hand-off)exact
phase.hasRightAnswer / .throughLinebeat.hasRightAnswer / .throughLineexact
phase.talkItThrough / .calibration[]beat.debrief.talkItThrough / .calibration[]exact
scene.setup[] / .pivotbeat.entry.beats[] / .signpostexact
scene.actionCalibration + outcomesbeat.calibration + character.reactionsfolded per-tier outcome narration → reaction
scene.characters[] (Jake, Marshall)beat.character (single: Jake)v1 limit one counterpart; multi-cast is Ensemble

Artifact 2 — scenario-live.html?type=<id>

The extracted generic player. It is the reference tier-ladder runner with the type-resolution seam rewired to ?type= (three lines) plus the recipe type module loaded. The runner itself is unchanged — it drives whatever the resolved type’s toMixArc() hands it:

REQ = ?type= || mix-arc
src = REQ.store.loadPublished() || REQ.DEFAULT
BA_SOURCE = REQ.toMixArc ? REQ.toMixArc(src) : mixArc.normalize(src)
SYSTEM_PROMPT = mixArc.compile(BA_SOURCE)  → the one shared runner (unchanged)

What was observed (live model, worker on an allow-listed origin)

  • (a) scenario-live.html?type=guided-arc booted the Marshall scenario from Guided Arc’s own DEFAULT (no manual publishing): establishing card → video intro → verbatim reflection prompt → a live model calibration turn (“You clocked the two things that matter most…”) → auto-advance → verbatim Beat 1 hand-off. Zero console errors.
  • (b) toMixArc(GuidedArc.DEFAULT) → isValid: true, 3 beats, 0 error / 0 warning lints; compile() = 19,277 chars (~4,819 tokens). The same composition played through to Beat 1 on the runtime, with the reflection graded as non-evaluated calibration exactly as authored.
  • Genericity — the same page at ?type=mix-arc renders mix-arc’s own default (“Speaking Up in the Moment”), a different scenario. One page, no per-type branches.
Honest note on “no regression.” Running Guided Arc through the tier engine is a deliberate upgrade: it gains explicit calibration tiers and a maxTurns cap in place of the older one-probe heuristic. The learner-visible pedagogy (verbatim locked beats, calibration-only reflection, right-answer coaching, debrief opener) is preserved. Two fidelity items to decide before flipping Guided Arc’s previewUrl: the single-counterpart roleplay limit (fine for Marshall — Jake is the sole counterpart; Ensemble covers true multi-cast) and folding per-tier scene outcome narration into reaction guidance.
5

Recipes as templates over one runtime

The same mapping that plays a recipe on the shared runtime also lets a curated recipe open as a pre-filled Mix & Match composition an author can then edit.

“Start from the Marshall shape” runs toMixArc() and drops the result into the Mix & Match editor: a 4-part composition (reflection + two coach-led beats + one roleplay beat) with the SME playbook attached, fully editable. Curated recipes stay the fast on-ramp; free-form composition stays the ceiling; both are the same scenario object over the same player. This is the P1 bet in the release-readiness brief, now with its enabling transform built and proven.

Migration plan — additive, sign-off-gated

Nothing here is a big-bang. Each step keeps all eight shipped types working, and each type joins the shared runtime only when its own flip is proven.

P0

Sign-off on direction (this document)

  • Confirm the target: converge on the tier-ladder engine; retire marshall-live / -v2 in favor of the guided-arc type on the shared runtime.
  • Confirm the two fidelity calls (single-counterpart roleplay; outcome-narration folding) are acceptable for Guided Arc, or scope Ensemble-style multi-cast into the runtime contract first.
P1

Extract the shared runtime, migrate the ladder family

  • Lift the byte-identical runner into js/sim-player.js + a shared page scaffold (the ~40 DOM ids are already identical across pages). Because the four tier-ladder runners are byte-identical, this is a lift-and-share, not a rewrite.
  • Extract coachNode (reconcile strategy) + grouping/prompt-lift into a shared component; the DOM and classes are already uniform across 16 pages.
  • Migrate onto scenario-live.html?type= one type at a time by flipping previewUrl(): mix-arc (native) → branching → ensemble (adds deliverFirstPhase) → scene-sweep (perception wrapper as a flag) → guided-arc (via toMixArc). A/B each against its frozen archive copy before the next.
  • Ship recipes-as-templates — the “Start from the <recipe> shape” entry point over toMixArc().
P2

Polish — shared list helper

  • Promote mix-arc’s collapsible/reorderable beat editor into a studioApi.collapsibleList() sibling of rowsBlock, then adopt it in the other list-heavy types (ensemble cast, scene-sweep hazards, guided-arc turns).
