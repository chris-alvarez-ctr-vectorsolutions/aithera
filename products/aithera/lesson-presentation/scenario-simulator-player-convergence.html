One engine, many pedagogies

The authoring side was always a single shell. The runtime is now too: one ?type=-routed player — scenario-live.html over one extracted engine, js/sim-player.js — drives all five scenario types with no per-type branches (scene-sweep converged via the opt-in perception module — §9). The engine is prescriptive about the shape of a run and flexible about what fills it. The parts that must stay consistent and safe are fixed by the engine; the parts a pedagogy defines are supplied by the type.

Converged · shipped to main

One page, one engine, four types

mix-arc, guided-arc, branching-arc and ensemble-arc all play on scenario-live.html?type=<id> over the extracted SimPlayer engine. Each was A/B’d byte-identical against the frozen archive before its flip; the bespoke per-type pages are frozen, and the learner launches the converged player.

The one design idea

A prescriptive spine, flexible fillings

The engine fixes the skeleton of a run — warm-up → tier ladder → graded close, app-owned advancement, locked hand-offs, a strict turn contract, compiled-in safety floors — and lets each type vary only the fillings. This split lets one runtime serve every pedagogy without a per-type branch.

New to the vocabulary? type, scenario, beat, phase, tier, native and recipe are defined in the glossary.

Where it landed

The runtime now has the same shape the studio always had: a type-agnostic shell. You extend it by adding a type module; the player itself does not change.

js/studio-shell.js was always type-agnostic — grep it for type.id === and you get zero hits. The runtime lagged: the learner-facing “ladder runner” (runArcEngine / closePhase / applyDeliver / arcStateBlock / entryBeatsFor) was copy-pasted across live pages in three engine generations. The four tier-ladder pages ran a byte-identical copy of that runner, so extracting it was a move rather than a rewrite. It now lives in one file, js/sim-player.js.

2

A prescriptive spine, flexible fillings

The engine fixes the parts of a run that must be identical for every learner, and leaves the parts a pedagogy defines to the type. Each concern below sits on one side or the other of that line.

Prescriptive — the spine

The engine owns the run

The app decides advancement; the model does not. Whatever the pedagogy, every scenario runs the same skeleton: a non-graded reflection warm-up, a tier ladder of phases, and a graded close with a report. Hand-offs between phases are locked, app-authored text — the model is given them but cannot rewrite them. A per-turn [SYSTEM STATE] line tells the model which phase is live and its turn budget. Turns come back as strict JSON. Safety floors are compiled in and cannot be authored away.

Flexible — the fillings

The type owns the content

Everything a pedagogy legitimately differs on. How many phases; each in which world (coaching vs live scene); with what tier bands and which authored transition each tier fires. Whether a scene has one counterpart or a whole cast. Whether the cold open is a video, a narrated audio brief, or a reading. The coach’s voice. What the playbook and resources say. A type declares all of this as data and the engine renders it — adding a pedagogy never edits the player.

3

The prescriptive spine, in detail

What every scenario gets, regardless of type. This is the runtime counterpart to the authoring contract in README.writer-studio.md; these elements are fixed for every type.

  • App-owned advancement. The model only classifies (reports a tier) and voices (writes the bubbles). The app decides stay-vs-advance from action / tier / the turn cap and routes. runArcEngine + closePhase are the sole authority — the model never advances itself.
  • The run spine. phaseIdx = -1 is the reflection warm-up (calibrate only, no tier, one clarifying probe max) → phases[0…N-1], each a world + a maxTurns cap + a recorded tier → phaseIdx ≥ N is completion, where the model must set complete:true with a report.
  • Locked entry beats. closePhase cues turn.deliver; applyDeliver appends the app’s own bridge / signpost / scene-open, picks the bridge variant the recorded tier calls for, and strips any copy the model reproduced so each hand-off appears once.
  • The [SYSTEM STATE] line. arcStateBlock injects, every turn, which phase is live (N/total, world, counterpart), turns used vs cap, the ladder so far, and the session-state vars. At the cap, the state line requires the model to teach and report.
  • The strict turn contract. JSON only: turn[] (speaker coach | you | character × kind coaching | dialogue | narration | clip) + action (continue | teach | redirect) + tier + deliver + complete + report + mode + inputTarget. The client renders from speaker+kind, not from the text content.
  • Tiers & transitions. A phase closes on a model-reported tier; the app records it, then applies the phase’s authored transitions[] — session-state writes, which phase is next, and which bridge variant opens it.
  • One canonical phase shape. { id, label, world:'coaching'|'scene', maxTurns, counterpart, calibration[].tier, transitions[], entry{…}, debrief.talkItThrough }. Every type’s toRuntime emits this shape. Because the shape is single, the engine needs no per-type branch.
  • Say / do split. A scene turn splits the learner’s input into a DO (narration) and a SAY (bubble) — one scene grammar across every roleplay type.
  • Compiled-in safety floors. A character-conduct floor sits in every scenario; branching adds a threat-content floor, ensemble a minor-safeguarding floor. They are written into the prompt at compile(), over and above any authored guidance, and an author cannot disable them.
The model classifies and voices; the app routes. Every decision that must be consistent across learners — when to advance, what a hand-off says, when to grade, when to stop — belongs to the app.
4

The flexible surface: two ways a type plugs in

A type reaches the shared engine one of exactly two ways. The resolver picks which with a single truthy check, then never branches on the type again.

Shape 1 · native

Owns its own toRuntime + compile

mix-arc, branching-arc, ensemble-arc, scene-sweep. A native type maps its own schema into the canonical phase shape (toRuntime) and writes its own system prompt (compile), with its own floors and guardrails. It plays directly, with no intermediate conversion.

Shape 2 · recipe

Expresses itself via toMixArc()

guided-arc. A recipe has no ladder of its own. It exposes toMixArc(), which restates it as a mix-arc composition, and then plays as mix-arc — mix-arc’s toRuntime + compile on that source. This conversion applies only to recipes.

mix-arc is the general case: a Mix & Match scenario is an ordered list of beats (coach-led / roleplay / observe), and a beat is a phase. So every other pedagogy expresses itself as either a native map onto that shape or a recipe that restates itself in it. The resolver is the whole seam:

REQ = ?type= || mix-arc
REQ_TYPE = Studio.get(REQ) || TYPE_GLOBALS[REQ] || mix-arc
IS_RECIPE = typeof REQ_TYPE.toMixArc === 'function'
PLAY_TYPE = IS_RECIPE ? mix-arc : REQ_TYPE
PLAY_SRC  = IS_RECIPE ? REQ_TYPE.toMixArc(src) : src
ACTIVE_SCENARIO = PLAY_TYPE.toRuntime(PLAY_SRC)
SYSTEM_PROMPT  = PLAY_TYPE.compile(PLAY_TYPE.normalize(PLAY_SRC))
  → SimPlayer.makeLadder({ scenario, state, fillT }) — the one shared engine
No per-type branches below the resolver. Authorable types resolve from the Studio registry (AitheraStudio.get); live-only types (branching, ensemble, scene-sweep — their Studio editors are stage 2) resolve via a window global. The runner never references a type name — grep it and you find none, the same as studio-shell.js.

7

Recipes double as editable templates

The same toMixArc() that plays a recipe on the shared runtime also lets a curated recipe open as a pre-filled Mix & Match composition an author can then edit.

“Start from the Marshall shape” runs toMixArc() and drops the result into the Mix & Match editor: a composition (reflection + two coach-led beats + one roleplay beat) with the SME playbook attached, fully editable. Curated recipes are the fast on-ramp; free-form composition is the ceiling. Both produce the same scenario object and run on the same player, so a recipe and a hand-composed scenario are identical at runtime.

8

Multi-cast conversations & fresh panels

The composed-beat model extends cleanly to two things real scenarios need: more than one live character in a scene (shipped in ensemble), and several distinct conversations across a run, each with its own surface but one shared memory (proven in a spike, folds in next).

A scenario groups its beats into conversations. A coaching conversation is the one persistent guide; a character conversation is a scene whose beat carries a small cast[] (2+ characters, reusing ensemble’s per-character model — driver, reactions, style). The learner acts “at the room” and the model voices whoever reacts — the runtime already renders multiple named speakers via m.name, so this is mostly a schema addition. A new character conversation opens a fresh panel; the model keeps the entire transcript.

Why fresh panels are cheap to add. There is exactly one source of truth — a single state.messages array — and the visible surfaces and the model’s memory are already independent projections of it. The coach panel already self-resets each stretch (it renders only the trailing run) while memory keeps growing; only the scene stage renders every scene bubble. So the entire runtime add is: a conversation tag on messages + a filter on the scene stage (the convStart filter) so it starts fresh like the coach panel already does — plus a one-line [SYSTEM STATE] cue telling the model “new conversation with X; you remember the rest.” Memory is never rebuilt: getTurn sends the whole array every turn.

Proven in a spike (scenario-multiconv-spike.html)

An end-to-end demo on the real SimCore turn engine: Conversation 1 is a two-character scene (Alex + Sam arguing; the learner mediates — both react as distinct people). After a couple of moves it hands off to Conversation 2 — a 1:1 with Sam that opens in a fresh panel (the argument is off-screen). Sam then references the earlier scene unprompted (“having that play out in front of everyone…”, “I appreciate you stepping in…”) — the banner confirms 13 prior messages carried in memory that the panel never shows.

The one non-native ingredient: perception

✅ Done. Scene Sweep now plays at scenario-live.html?type=scene-sweep, built exactly along the design below. Verified live end-to-end (mark → cross → coach credits + coverage-driven nudge → coverage rail → close) and A/B byte-identical to the frozen archive on every behavioral essential; the four conversational types re-verified unchanged.

Four types converged cheaply because they are the same conversational interaction the shared player already renders. Scene Sweep was the exception: one half of it is conversational and already shared, the other half is not.

Scene Sweep’s conversational half — the Observe / Remediate coach beats — was the shared player already. Its perception half — tapping the hazards on a photo — was ~575 net-new lines the conversational player had no concept of, plus two structural reconciles to the shared engine that all four shipped types depend on. Rather than inline that into the player, it went into an opt-in module (js/sim-perception.js) that mounts only for a kind:'spot' phase — so the four conversational types take none of its code path.

Perception cannot be an ordinary ingredient because sim-player.js is DOM-free — the runtime sibling of studio-shell.js, operating only on { scenario, state, fillT }. Perception is DOM-aware (a photo, a tap surface, focusable regions, a coverage rail), so it gets its own mountable module rather than living in the engine:

FileChange
js/sim-perception.js newSimPerception.mount({ host, scenario, state, fillT, onCross }) — the sweep stage + keyboard/region + free-text a11y paths + coverage rail, driving state.covered. DOM-aware sibling of sim-player.js; reuses the already-shared SceneSweepGeo.
js/sim-player.jsExtend, guarded on kind==='spot': a coverage state-block line. The other four types have no spot phase, so they emit nothing new.

The rule this keeps. A type adapts to the engine in its toRuntime (normalizing flat phases into the canonical shape); the engine does not add a per-type branch to accommodate it. DOM-aware code lives in its own mountable module, not in the DOM-free engine. Full staging, each step A/B’d vs the frozen archive, is in SCENE-SWEEP-CONVERGENCE-PLAN.md.
10

How it stays converged

Four mechanics keep the single engine from re-forking over time.

PressureContainment
A type’s extras don’t fit the canonical phase shapeThey ride the same engine as data or flags (spotted, deliverFirstPhase, cast[]) rather than a fork. Native types own toRuntime+compile, so their extras are not flattened; only recipes take the conversion.
A change regresses a converged typeEvery flip is additive and A/B’d byte-identical vs the frozen archive/2026-08-04/ (tag archive/pre-option-b-2026-08-04), one type at a time, proven before the next.
The engine grows a per-type branchThe phase shape is single and canonical — a type adapts in toRuntime, never in the engine. sim-player.js stays DOM-free; anything DOM-aware (perception) goes in its own mountable module.
Shared JS/CSS serves stale to other live pagesBump each file’s ?v= everywhere it loads + the service-worker version, per the repo’s cache-bust rule.
Where it stands

The runtime now mirrors the studio: one shell, type-agnostic, extended by adding a type module rather than editing the player. All five types are converged and shipped, each proven byte-identical to the bespoke page it replaced.

The flexibility is bounded on purpose. A prescriptive spine — app-owned advancement, locked hand-offs, a strict turn contract, compiled-in safety floors — keeps every learner’s run consistent and safe. Flexible fillings — worlds, tiers, transitions, cast, intro modality, voice, playbook — are left to the type.

Glossary

These terms recur throughout and are easy to run together. Grouped by what they describe rather than alphabetized, so the pairs that blur — beat/phase, type/scenario, native/recipe — sit next to each other.

TermMeaning
TypeA scenario pedagogy — mix-arc, guided-arc, branching-arc, ensemble-arc, scene-sweep. In code, a module exposing DEFAULT / normalize / compile / toRuntime (and, for a recipe, toMixArc). Selected at runtime by ?type=.
ScenarioOne authored instance of a type — the Marshall scenario is a guided-arc scenario. The type is the template; the scenario is the filled-in content.
PhaseOne step of a run in the engine’s canonical shape. It lives in a world, has a turn cap, and closes with a tier. The engine indexes scenario.phases[].
BeatThe authoring word for a phase, used in mix-arc: one unit of the composition carrying one interaction kind (coach-led / roleplay / observe). A beat becomes a phase at runtime — beat and phase are the same thing on the authoring and runtime sides.
WorldWhether a phase runs as coaching (the learner talks with the coach) or scene (the learner acts opposite a character).
LadderThe ordered sequence of phases the learner climbs. The “tier-ladder engine” is the shared runner (SimPlayer) that drives it.
TierThe calibration band the model reports when a phase closes — how well the learner handled it. A tier fires the phase’s transitions and selects the next hand-off’s bridge.
TransitionAn authored rule on a phase: on a given tier, write session state and route to a named next phase.
Hand-off / entry beatsThe locked, app-authored lines that open a phase — bridge + signpost + prompt, or a scene open. The model is given them but cannot rewrite them.
Reflection warm-upThe non-graded gut-check before the ladder (phaseIdx = -1): calibrate only, no tier.
Native (type)A type that owns its own toRuntime + compile and plays directly on the engine.
Recipe (type)A type with no ladder of its own that restates itself as a mix-arc composition via toMixArc(), then plays as mix-arc. guided-arc is the one recipe today.
toRuntime()A type method that maps its own schema into the engine’s canonical phase shape.
toMixArc()A recipe’s method that restates its scenario as a mix-arc composition.
compile()A type method that produces the system-prompt string sent to the model.
FloorA locked safety block compiled into every scenario — conduct (all types), threat (branching), minor-safeguarding (ensemble). An author cannot disable it.
ConversationA distinct stretch of dialogue with its own panel — the persistent coach, or a character scene. Separate panels, one shared memory.
