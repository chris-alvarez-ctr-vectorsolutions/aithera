§A · The map

Their practice is our rung; their phase is a layer above

The v4 phase is a story segment shown to the learner as "Phase 2 of 3" — a grouping of exactly one practice and one debrief. Our ladder has no such grouping (our level is a cosmetic label). Their practice is the turn-owning rung — that's our phase. Their debrief is a second rung we express as fields today (§D-2).

§C · The output contract

The wire — the surface we never mapped new

The earlier note aligned the authored shape. The dev repo also fixes the runtime shape: POST /api/v1/conversations/{id}/messages (app/schemas/conversation.py). This is the integration surface a player consumes, and it's where two of our "deltas" become concrete rather than aspirational.

Turn request / response — the shapes that matter

// REQUEST — the service is STATELESS: every call carries the whole state
{ scenario_id, model_id, input, active_phase_id,
  history: ThreadedHistory | HistoryEntry[],   // dual-history preferred
  invoke_closing: bool,   // the "see my feedback" tap — not a stage, no id, no turn
  coach_help: bool }      // sidebar "ask the coach" mid-scene; budget- + advancement-inert

ThreadedHistory = { coach: [...], practice: { <phase_id>: [...] } }   // two-conversation model, ON THE WIRE

// RESPONSE
{ history, phase_id, category, conversation_ended, ready_for_closure,
  next_phase_id,           // SERVER's advance signal; may be a phase BEHIND (retry route)
  next_practice_phase_id,     // where "Continue practicing" re-enters
  spotted: [rubricId…],     // observe only — cumulative coverage = our rail
  threads,
  closure: ClosureBlock? }     // only when conversation_ended

ClosureBlock = { final_feedback:[{label,body}]?,   // model recap/strengths/growth
                 component_groups, summary, source_references,  // ideal_response, VERBATIM
                 score? }                          // present on topic_match — see §E-5
// Streaming mirrors this: SSE delta events + a done event = the buffered response.
  • Stateless, client-held history — the service holds no session; scenario_id + history ride every call. That's our model too (the player holds state client-side), so we align on the hardest-to-retrofit property for free.
  • ThreadedHistory {coach, practice} is delta #1 made real — the two-conversation isolation isn't just prose in §2, it's the wire's history shape, practice keyed by phase id.
  • Advancement is a returned signal, not a client decision — next_phase_id is the server's stay/advance verdict. And it "may be a phase behind" for a debrief→retry route — a backward edge (§E-1).
  • spotted is our coverage rail, and closure is our results screen + playbook — ideal_response shipped verbatim, per-learner feedback as labeled sections.
§D · What differs — our side

Four sharper calls, now confirmed in shipped v4

These are the gaps between our reference and v4 — the ones our engine is closing in the current update. All four are confirmed in the schema/wire, not just the spec.

1

Two threaded conversations. they're ahead on the wire

Confirmed by ThreadedHistory {coach, practice} (§C): the practice runs as its own history the coach prompt never sees. Teaching (teaching_points, misconceptions, key_points, ideal_response) is debrief-/closing-scoped; a scene sees only its thread plus authored carryover. We run one static compiled prompt and keep teaching out of scenes by instruction.

Adopting. The stronger anti-leak guarantee — and because it's on the wire, our promptHash can't equal theirs per-run: conformance must hash per-scope (§G).

2

The debrief is a first-class unit; ours is two fields.

The v4 debrief ({phase_id}.debrief) owns turns via follow_up_turns (schema enforces 0 ⇒ delivery-only: final_word required, probe/requirement/input_placeholder forbidden), carries key_points, its own levels, and an optional locked probe. Ours is talkItThrough + points, one teach turn.

Low-cost, and it unlocks #1. Promoting our debrief to its own rung is a normalize-time transform, and an independently-scopeable debrief is what makes the two-conversation split buildable.

3

Cross-scene memory is a verbatim transcript, not a summary. they're ahead

Scene-scoped carryover: [{from}] grants a later scene the earlier practice's verbatim transcript — "never a summary." Our transitions[].set writes exactly that summary (a disposition string). Same goal, opposite mechanism; they rejected ours on purpose.

Adopting. No shipped scenario of ours routes on tier — every transitions[] converges on one next, varying only set — so set is only ever carry-forward, which a transcript does better.

4

A fixed 3-level scale vs our open tier vocabulary. decision

The schema fixes the scale: levels requires unthoughtful / neutral / strong, author writes only look_for / response. Our calibration[].tier is author-defined; mix-arc ships CONNECTS / VAGUE / CONFRONTS — which won't port to the fixed set.

Our call — and the recommendation stands: don't push for more. A level is a trace-only response-selector, not a learner grade; three coaching moves (redirect / nudge / affirm) cover it, and more buckets degrade classifier reliability. Concede the custom names (cosmetic; the model classifies on look_for), and bring a single un-authorable scenario if one truly exists rather than an abstract ask.

§E · Spec vs implementation

Where the v4 target is still settling align to spec, verify vs build

The realization is real, but the dev team's own spec-alignment-audit and v4-migration-report record places the engine hasn't caught up to the spec we aligned to. This matters directly: if our reference conforms to the spec and the shipped engine does something else, "matching v4" has to name which. These are the contract-level ones — stated neutrally, not as their bug list.

  • Forward-only vs a backward retry edge. The spec says no route backward; the wire's next_phase_id is documented to "may be a phase behind" so a debrief/gate can send the learner back to re-attempt a failed practice. So there is a retry edge — which actually maps to a retry concept we could adopt, but it contradicts the flat "forward-only" framing both docs used.
  • Server-owned advancement vs reply-shape advancement (coach units). Spec: the server decides from the declared exit.requirement + budget. Today a coach unit advances on the reply's punctuation/intent marker and the requirement isn't consulted — it's authored-but-not-yet-enforced on coach turns. If we honor requirement in our engine, we'll be stricter than the current build.
  • spot_target gating. Spec: "the target only gates completion." Today scene/observe advancement is model-marker-driven; spot_target bounds the rubric and the meter but has no server-side completion gate yet.
  • Prompt scoping at the opening. Spec §2: teaching withheld from practice/opening prompts. Today teaching_points / misconceptions render into the opening prompt. The isolation we're adopting (§D-1) should follow the spec here, not the current build.
  • Trace-only assessment vs a learner-facing score. Spec §2 / §8: internal assessment never reaches the learner and the close authors no score. The output ClosureBlock carries an optional score (topic-match) a surface can render. If we mirror the output shape, don't surface score.

The one operational takeaway

Align our reference to the spec (the stable target), but pin the build when we run conformance — because a snapshot taken against today's engine encodes these in-flight divergences, not the contract. When the engine closes them, re-pin.

§F · The envelope & the layers

Both settled in our favor

Envelope: v4's root is { implementation_id, modality, schema_version, content } — the learning_objective/implementations[] wrapper is gone; the schema title even reads "implementation-root," and LO identity "belongs to the surrounding content system." Our scenario object is their content; we stay the payload. The only design question left is the picker UX for choosing among implementations, which marshall-mode-select already prototypes — a mock, not an engine change.

Layers: v4's design constraint 1 — "content carries no prompt text; deterministic serializers render prompts" — is our authored-source → toRuntime / compile split, stated as a hard rule and enforced by a lint. Same three layers; v4 polices the data/prompt seam harder than we do.

§G · Conformance

Proving the two engines agree

There are now two contracts to conform to, not one: the authored schema (lo_cml_v4.schema.json) and the turn/wire shape (conversation.py). js/sim-snapshot.js already hashes the authored→runtime→prompt derivation; the wire adds a second checkpoint — same authored source should produce the same next_phase_id / spotted / closure decisions.

Two caveats, both from above: adopting two-conversation scoping (§D-1) means a whole-run promptHash is meaningless — hash per-scope (coach prompt and each scene prompt separately). And because spec and engine diverge (§E), a conformance run must pin the engine build it targets, or it will encode in-flight divergences as if they were the contract.

§H · Decisions

What's on us now

  • Adopt the two-conversation model (§D-1) — now confirmed as the wire's ThreadedHistory, not just spec prose. Changes what conformance means.
  • Promote the debrief to a first-class unit (§D-2) — low-cost, and the enabler for the split.
  • Swap disposition summaries for verbatim carryover (§D-3) — clean upgrade; our set is only ever carry-forward.
  • Fixed 3-level scale (§D-4) — my read: concede it; bring one un-authorable scenario if it exists, not an abstract ask.
  • Align to the spec, pin the build for conformance (§E) — the divergences are the engine's to close; our reference should track the contract, not today's build.
