Aithera · Scenario Simulator

Every scenario type shares one runtime shape.

A scenario object carrying a phases[] ladder, produced by type.toRuntime(source) and driven by one engine, js/sim-player.js. This page documents that shape and the fields the engine reads.

Reference build scenario-live.html · js/sim-player.js Engine core ~220 lines, DOM-free Runtime types mix · branching · ensemble · scene-sweep · guided
§1 · The shape

One object, one ladder

Every type produces the same object: a common core, three keys the engine adds (phases, opening, sceneLineCaption), and additive blocks that appear only where a type needs them. The engine drives the phases[] ladder; the rest is context and prompt material.

Types differ by which slots they fill and which additive blocks they carry — the backbone is constant.

Runtime scenario object

{
  // common core — carried from the authored source
  title, course, learnerName, characterName,
  framing, learnerRole, establishing,
  intro:      { type: 'reading'|'audio'|'video', audio:{…}, video:{…} },
  voice:      { persona, guidance },
  reflection: { prompt, feedbackGuidance, enabled },
  playbook, resources,

  // added by toRuntime() — every type
  phases:  [ /* the ladder — §2 */ ],
  opening: [ "…reflection warm-up bubble(s)…" ],  // [] when reflection is off
  sceneLineCaption: "You",

  // additive — only where a type needs it
  state?:    [ { key, label, initial } ],            // mix · branching · ensemble · guided
  cast?:     [ { name, baseline, driver, reactions } ], // branching · ensemble
  canon?:    [ "continuity fact", … ],              // branching · ensemble
  coverage?: { required, total },                   // scene-sweep
  hazards?:  [ … ],  decoys?: [ … ],  scene?: { … }  // scene-sweep
}

Machine-readable json schema

This shape as a validatable JSON Schema (draft 2020-12): scenario-simulator-runtime.schema.json. Fields the engine reads carry an x-engine-reads annotation. Validated against toRuntime(DEFAULT) for all five types.

§2 · The phase

The phase — one rung of the ladder

Three authored flavors normalize to one skeleton: a lean ladder phase (branching, ensemble), a rich beat phase (mix, guided — adds type, character, media), and a perception phase (scene-sweep — uses kind and flat signpost/prompt that toRuntime folds into entry). The engine reads a small subset (§3).

Phase object

{
  id: "meeting",
  world: "coaching" | "scene",        // scene-sweep uses kind: "spot"|"act"|"prevent"
  counterpart: "Ray" | "" | "Narrator",  // who the learner faces in a scene
  maxTurns: 6,                            // the app's turn cap

  entry: {                               // the locked, app-authored open of the phase
    bridge: "", bridgesByTier: { STRONG:"…", NEUTRAL:"…" },  // prior tier picks the opener
    signpost: "…", prompt: "…",
    beats: [ { speaker, kind, text, name? } ],  // scripted scene open
    cta: "Step into the room"
  },

  calibration: [ { tier: "STRONG", guidance: "…" } ],  // tier vocabulary
  debrief: { talkItThrough: "…", points: "…" },        // talkItThrough = the teach-opener

  transitions: [
    { onTier: "STRONG", next: "escalation", set: { disposition: "…" } }
  ]
}
§3 · The contract

What the engine reads

The ladder engine reads only the fields below. Everything else is the model's job (the prompt) or a render surface's (§7).

FieldRead byWhat it decides
scenario.phases[]whole engineThe ladder, indexed by state.phaseIdx. The app is the source of truth for which rung is live.
phase.maxTurnsrunArcEngineThe turn cap. At the cap the app forces the model to resolve and report.
phase.worldapplyDeliver"scene" enters scene mode and addresses input to the character; else coaching.
phase.entry.*entryBeatsForThe locked opener: bridgesByTier[prevTier] selects the bridge, then signpost, prompt, scripted beats.
phase.media.segments[]entryBeatsForLocked stimulus cards — a clip or a forwarded message — shown before the coach speaks.
phase.transitions[]{ onTier, next, set }closePhaseThe recorded tier selects the next phase id and writes session state.
phase.debrief.talkItThroughrunArcEngine (fallback)The verbatim teach-opener. The model's action field is the primary phase-close signal (see the callout below); this string-match is only the fallback used when a turn omits action — and it is matched case-, space- and punctuation-insensitively against the first coach bubble, not by raw equality.
phase.counterpartapplyDeliverThe character the learner faces in a scene.
scenario.state[]{ key, label, initial }arcStateBlockSession variables shown on the [SYSTEM STATE] line and written by transitions.
phase.kind + ctx.outcomeBlockarcStateBlock (optional hook)A custom render surface opts in on kind (scene-sweep). No hook, no surface code runs.

Control flow belongs to the app — the model reports, it does not navigate

The app decides which phase is live and when to advance. Each turn the model returns dialogue plus a structured action — "continue" (stay in the phase), "teach" / "probe" (land the point / one Socratic follow-up), or "redirect" (the input was not an answer) — and, when it closes a phase, a tier. The action field is the primary phase-close signal; the talkItThrough string-match above is only the fallback for a turn that omits it. Reading the cap, recording the tier (validated at run time against the phase's calibration vocabulary), applying transitions[], and appending the next locked entry are all app logic. The same engine drives a coaching chat, a role-play, a multi-character ensemble, and a spot-the-hazard canvas.

§4 · Two outputs

Data and prompt

Each type emits two things from the same source:

  • toRuntime(source) → a JSON object — the phases[] ladder the engine drives (§1–§3).
  • compile(source) → a system-prompt string — the arc, character models, guardrails, and turn contract the model reads.

Most per-type variation lives in the prompt. Compiled prompt sizes:

TypePrompt sizeWhat it carries beyond the shared rules
mix-arc~18.1kComposed beats, one voice.
scene-sweep~22.2kCoverage contract, hazard rubric, look-again nudging.
guided-arc~24.3kCompiled via mix-arc after toMixArc() (§5).
branching-arc~32.4kTier-contingent bridges, the cast model, the threat floor.
ensemble-arc~37.9kMultiple cast models, earned disclosures, the minor-safeguarding floor.

A field belongs in the JSON when the engine or a render surface reads it. Model instructions live in the compiled prompt.

§5 · Two paths

Native and recipe types

A type reaches the engine one of two ways. Four are native — they own toRuntime and compile and play directly: mix-arc, branching-arc, ensemble-arc, scene-sweep. One is a recipe — guided-arc expresses itself as a mix-arc scenario via toMixArc(source), then plays as mix-arc.

The funnel shows in the data. Guided-arc's runtime keys are mix-arc's, including fields its authored source never had:

The recipe funnel

guided-arc authored keys:  … phases, scene, contextSource, previousLO
        │
        │  toMixArc(source)
        ▼
guided-arc runtime keys:   … state, beats, threatContent, involvesMinors, phases, opening, sceneLineCaption

The split is deliberate. Branching's tier transitions, ensemble's cast and earned disclosures, and scene-sweep's perception subsystem have no mix-arc equivalent, so those types keep their own runtime rather than round-trip through it.

§6 · Two layers

Authored source and runtime

The authored source is what a human edits and what the tool exports. It differs per type: mix-arc authors beats[]; branching, ensemble, and scene-sweep author phases[]; guided-arc authors phases[] plus scene. The runtime is derived from it by toRuntime() at load.

normalize(source) fills defaults and forward-migrates older authored JSON (mix-arc's migrateV2, guided-arc's beats→phases), so an older export still loads.

What the export contains

The Export button serializes the normalized authored source — the runtime and the compiled prompt are derived, and are not included.

  • branching · ensemble · scene-sweep — phases authored directly, so the export closely matches the runtime, minus the three engine-added keys.
  • mix-arc — exports beats[]; the runtime phases[] are derived.
  • guided-arc — exports phases[] + scene; the runtime is a mix-arc object via toMixArc.
  • The system prompt is generated at play time by compile().

Run a source through type.toRuntime() and type.compile() to reproduce both.

§8 · Design

Why one engine holds every type

  • One canonical runtime shape — a phases[] ladder every authoring format normalizes into.
  • Control flow is app logic — turn caps, tier recording, transitions, and the next locked entry. The model supplies dialogue and a tier.
  • Data and prompt are separate outputs — toRuntime for the engine, compile for the model.
  • Transitions carry branching — { onTier, next, set } records the tier, writes state, and picks the next rung.
  • One surface hook — keyed on kind, it mounts a custom renderer (scene-sweep's perception canvas). Absent, the ladder runs unchanged.
  • normalize() forward-migrates authored JSON — content survives schema change.
§9 · Conformance

Building an engine that matches this one

This player (scenario-live.html + js/sim-player.js) and the Writer Studio that authors its JSON are the working reference for the production engine. Below is what a port must preserve, what this code already enforces for you, and what stays yours to build. The risky parts are the seams between the deterministic engine and the probabilistic model — tier scoring, prompt/runtime agreement, and phase-close signalling — so those get the most attention.

Tiers have exactly one source of truth

A phase's calibration[].tier values are the tier vocabulary. compile() derives the prompt's tier list from them, transitions[].onTier routes on them, and the engine validates the model-reported tier against them at close — so the prompt and the runtime cannot disagree on the tier set by construction. Never introduce a second, hardcoded tier list. SimPlayer.lint() flags an onTier outside the vocabulary and a tier-routed phase that declares no calibration[].

The shape is discriminated — don't build a bag of optionals

One phases[] ladder is shared, but a phase is EITHER a coaching/scene rung (world) or a scene-sweep perception rung (kind), and the additive top-level blocks are type-scoped (state; cast/canon; coverage/hazards/decoys/scene). The runtime JSON Schema now tags every such field with x-applies-to and encodes the cross-type invariants as conditionals (a phase has world OR kind; a kind:"spot" scenario carries the perception blocks). In a typed language, promote this to a per-type discriminated union (oneOf on the discriminant) so invalid field combinations become unrepresentable, not merely catchable.

Guardrails this engine already runs — port them

  • The app owns control flow. Turn caps, tier recording, transitions, and the next locked entry are app logic; the model returns dialogue + action + tier and never navigates.
  • The reported tier is validated against the phase vocabulary; an off-vocabulary label is recorded (unreported) and routed on the default edge, not acted on.
  • Only declared state keys are writable. A transitions[].set write to an undeclared key is dropped (and warned); lint() catches it at load.
  • A next that resolves to no phase terminates the ladder — almost always an authoring typo, so lint() reports it before a run and the engine warns at close.

  "sourceSchemaVersion": 1,

  "runtimeHash": "1a2b3c4d",           // FNV-1a over key-SORTED runtime → language-portable
  "promptHash":  "9f8e7d6c",
  "promptChars": 30247,                // exact per-build prompt size
  "model": null, "modelSettings": null, "at": null
}
// Same source on both engines → equal hashes ⇒ they conform. Unequal ⇒ diff the
// runtime object / prompt string to find the divergence. scenario-live.html logs
// this record at boot: "[SimSnapshot] run conformance record".

Prompt assembly & the cache seam

Each turn the system prompt is compile(source) — static for the whole run — followed by the per-turn [SYSTEM STATE] line appended at its end (the only volatile part). Put the prompt-cache breakpoint at that boundary so the large static prefix is cached across turns, and never resend scenario content in the message history — the history carries only the conversation. Prompts run ~16–36k characters (§4); SimSnapshot.promptChars reports the exact current size per build.
