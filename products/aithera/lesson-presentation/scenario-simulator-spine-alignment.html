Scenario CML v4 and the universal player.

Scenario CML v4 (VectorLearning/scenario-simulator-poc) and the universal player (scenario-live.html + js/sim-player.js) are two implementations of the same conversational-scenario runtime. This note maps them field for field: the shared backbone, the four points where their data models differ, the runtime wire contract, and the points where the v4 specification and the shipped v4 engine currently disagree.

Grounding sources

Reconciled against a read of VectorLearning/scenario-simulator-poc: the authoritative schema (app/lo_schema/lo_cml_v4.schema.json), the turn/wire models (app/schemas/conversation.py), and the project's own v4-migration-report.md and spec-alignment-audit.md. Every field name in the crosswalk is verified against the schema. The schema selects one mode-shaped interaction via a oneOf on mode — a discriminated union with no forbid-lists.

§A · The map

The v4 practice is a rung; the v4 phase is a grouping layer

In v4 a phase is a story segment shown to the learner as "Phase 2 of 3" — a grouping of exactly one practice and one debrief. The universal player has no grouping layer; its level field is a cosmetic label. The v4 practice is the turn-owning unit where the learner acts, which corresponds to a single rung in the universal player. The v4 debrief is a second turn-owning unit; the universal player expresses it as fields on the rung (§D-2).

§C · The output contract

The runtime wire contract

The crosswalk above covers the authored shape. The v4 repo also fixes the runtime shape: POST /api/v1/conversations/{id}/messages (app/schemas/conversation.py) — the surface a player consumes. Two of the data-model differences below appear directly in it.

Turn request / response — the shapes that matter

// REQUEST — the service is STATELESS: every call carries the whole state
{ scenario_id, model_id, input, active_phase_id,
  history: ThreadedHistory | HistoryEntry[],   // dual-history preferred
  invoke_closing: bool,   // the learner's "see feedback" tap — not a stage, no id, no turn
  coach_help: bool }      // sidebar "ask the coach" mid-scene; budget- + advancement-inert

ThreadedHistory = { coach: [...], practice: { <phase_id>: [...] } }   // two-conversation model, on the wire

// RESPONSE
{ history, phase_id, category, conversation_ended, ready_for_closure,
  next_phase_id,           // server advance signal; may be a phase BEHIND (retry route)
  next_practice_phase_id,     // where "Continue practicing" re-enters
  spotted: [rubricId…],     // observe only — cumulative coverage = the coverage rail
  threads,
  closure: ClosureBlock? }     // only when conversation_ended

ClosureBlock = { final_feedback:[{label,body}]?,   // model recap/strengths/growth
                 component_groups, summary, source_references,  // ideal_response, VERBATIM
                 score? }                          // present on topic_match — see §E
// Streaming mirrors this: SSE delta events + a done event = the buffered response.
  • Stateless, client-held history — the service holds no session; scenario_id + history ride every call. The universal player also holds state client-side, so both align on the hardest-to-retrofit property.
  • ThreadedHistory {coach, practice} — the two-conversation model appears directly in the wire's history shape, practice keyed by phase id (§D-1).
  • Advancement is a returned signal — next_phase_id is the server's stay/advance verdict, and it "may be a phase behind" for a debrief→retry route (§E).
  • spotted corresponds to the coverage rail; closure to the results screen and playbook — ideal_response shipped verbatim, per-learner feedback as labeled sections.
§D · Data-model differences

Four points of divergence — all four now closed

These were the four places the v4 data model and the universal player genuinely differed, each confirmed against the v4 schema and wire rather than the specification alone. All four have since been resolved on the v4 route (?type=v4-universal); the native per-type routes are deliberately unchanged. The divergences are kept on the record because each one explains why the resolution took the shape it did — and because the sequencing turned out to matter.

1

Two threaded conversations vs one compiled prompt closed · scoping shipped

v4 runs the practice as its own conversation the coach prompt never sees (ThreadedHistory {coach, practice}): teaching (teaching_points, misconceptions, key_points, ideal_response) is debrief-/closing-scoped, and a scene sees only its thread plus authored carryover. The universal player used one static compiled prompt and kept teaching out of scenes by instruction — structural isolation versus isolation by instruction.

Resolved: js/scenario-v4-scopes.js implements the scoped model by redaction-recompile — each scope's prompt is the same shipped builder run over a redacted copy of the document, so the turn contract is identical in every scope by construction. A practice prompt no longer contains teaching content at all; a scene prompt carries one phase plus scene_world. Verified across all 11 v4 scenarios × every phase. The per-scope hashing implication for conformance (§G) now applies literally: there is no single whole-run prompt to hash.

2

The debrief is a turn-owning unit vs two fields closed · debrief rung shipped

The v4 debrief ({phase_id}.debrief) owns turns via follow_up_turns (schema-enforced: 0 ⇒ delivery-only — final_word required, probe/requirement/input_placeholder forbidden), and carries key_points, its own levels, and an optional locked probe. The universal player expressed the debrief as talkItThrough + points in one teach turn.

Resolved: an interactive debrief (follow_up_turns ≥ 1) is now its own rung carrying the derived id {phase_id}.debrief, with the locked probe delivered verbatim as its entry and probe.levels grading the answers. A delivery-only debrief emits no rung — the practice rung's fused close-teach already is that debrief — and its final_word is delivered verbatim as the next rung's locked bridge. The prediction below held exactly: this was the structural prerequisite, and it shipped first.

Original implication (recorded because it proved correct): promoting the debrief to its own rung is a normalize-time transform, and is the structural prerequisite for the threaded model (#1).

3

Cross-scene memory: verbatim transcript vs disposition summary closed · carryover consumed

v4's scene-scoped carryover: [{from}] grants a later scene the earlier practice's verbatim transcript — "never a summary." The universal player's transitions[].set wrote a disposition summary string. Both carried learner-dependent aftermath forward; the mechanisms differed.

Resolved with #1, and it could not have shipped before it: carryover consumption is a no-op in a single-conversation player — the model already sees every earlier turn, so a grant is trivially over-satisfied. Once scopes existed, it became real: a scene turn's history is its own rung slice plus the verbatim slices of the phases its carryover names, recorded through a guarded onRungEnter hook. The disposition-summary mechanism is retired on the v4 route.

4

A fixed 3-level scale vs author-defined tiers closed · scale adopted

The v4 schema fixes the scale: levels requires unthoughtful / neutral / strong, and the author writes only look_for / response. The universal player's calibration[].tier was author-defined per phase; mix-arc shipped CONNECTS / VAGUE / CONFRONTS.

Resolved by adoption, not by transform. The v4 scale is now the scale: custom tier labels are retired, and the conversion relabels each authored tier onto the fixed three by position. This was correctly called as the one difference no mechanical transform could reconcile — the resolution was to stop trying and adopt. The recovered detail: our authors had already written both halves v4 separates, so look_for was extracted from existing guidance prose at an 89% hit rate rather than rewritten.

On the substance: a level selects which coaching response plays rather than presenting a learner-facing grade, and three responses correspond to the coaching move-set (redirect / nudge / affirm); the tier labels carried no behavior the criteria do not.

§E · Spec vs implementation

Where the v4 spec and the shipped engine disagree spec ≠ build

The v4 realization is complete, but the project's own spec-alignment-audit and v4-migration-report record points where the engine has not yet caught up to the specification. These affect alignment directly: a reference built to the spec and an engine that behaves differently are not conformant. The contract-level items:

  • Forward-only vs a backward retry edge. The spec states no route backward; the wire's next_phase_id is documented to "may be a phase behind" so a debrief/gate can return the learner to re-attempt a failed practice. A retry edge therefore exists, contradicting the flat "forward-only" description.
  • Server-owned advancement vs reply-shape advancement (coach units). The spec has the server decide from exit.requirement + budget. In the shipped engine a coach unit advances on the reply's punctuation/intent marker and requirement is not consulted — authored but not yet enforced on coach turns.
  • spot_target gating. The spec states "the target only gates completion." In the shipped engine, scene/observe advancement is model-marker-driven; spot_target bounds the rubric and meter but has no server-side completion gate.
  • Prompt scoping at the opening. Spec §2 withholds teaching from practice/opening prompts. In the shipped engine, teaching_points / misconceptions render into the opening prompt.
  • Trace-only assessment vs a learner-facing score. Spec §2 / §8 keep internal assessment off the learner surface and author no score. The output ClosureBlock carries an optional score (topic-match) a surface can render.

Operational note

Alignment targets the specification (the stable contract); a conformance run pins the engine build it targets, because a snapshot taken against the current engine encodes these in-flight divergences rather than the contract. When the engine closes them, re-pin.

§F · Envelope & layers

Envelope and layer model

Envelope. The v4 root is { implementation_id, modality, schema_version, content }; the schema title reads "implementation-root," and LO identity, revisioning, and catalog metadata belong to the surrounding content system. The universal player's scenario object corresponds to v4 content. The remaining design question is the picker UX for selecting among implementations of one objective, which marshall-mode-select prototypes — a mock, not an engine change.

Layers. v4 design constraint 1 — "content carries no prompt text; deterministic serializers render prompts" — corresponds to the universal player's authored-source → toRuntime / compile split, stated as a rule and enforced by a lint. Both are three-layer models; v4 enforces the data/prompt boundary more strictly.

§G · Conformance

Conformance between the two engines

There are two contracts to conform to: the authored schema (lo_cml_v4.schema.json) and the turn/wire shape (conversation.py). js/sim-snapshot.js hashes the authored → runtime → prompt derivation; the wire adds a second checkpoint — the same authored source should produce the same next_phase_id / spotted / closure decisions.

Two caveats, both from above: the threaded model (§D-1) makes a whole-run promptHash meaningless, so prompts are hashed per scope (the coach prompt and each scene prompt separately); and because the spec and engine diverge (§E), a conformance run pins the engine build it targets, or it encodes in-flight divergences as if they were the contract.

§H · Summary

Where each divergence landed

  • Threaded conversations (§D-1) — closed. Scoping shipped as redaction-recompile; per-scope prompt hashing now applies literally for conformance.
  • Debrief as a turn-owning unit (§D-2) — closed. Interactive debriefs are their own rungs with derived ids; delivery-only ones ride the fused close-teach with verbatim final-word bridges.
  • Verbatim carryover vs disposition summary (§D-3) — closed with §D-1, and it could not have shipped before it: carryover is a no-op until scopes exist for it to punch through.
  • Fixed 3-level scale (§D-4) — closed by adoption. Correctly identified as unreconcilable by transform; custom tier labels retired.
  • Spec vs shipped engine (§E) — still open, and it is theirs, not ours. Five contract-level divergences inside POC V4 itself; alignment tracks the spec, conformance pins the build.

What this document is now for

Its reconciliation job is finished — the four divergences are closed and the live record of decisions, extensions and open questions is the alignment notes. What remains uniquely here: the field-for-field crosswalk verified against the schema (§B), the output/wire contract (§C), and §E's spec-versus-build divergences inside POC V4 — the last of which is still live input for the alignment conversation.
