Opening scenario authoring to customers

What has to change before external authors — people outside the K&A team — can create and edit scenario simulations on their own. Seven things to plan for, in rough order of how much they shape the architecture.

Premise the author is no longer trusted Rule of thumb durable work goes in the platform, not the editor 2026-08-31

The one-sentence version

Everything on this page is the same change seen from seven angles: today every author is Vector staff, so the tooling trusts the author completely — it shows them the composed prompt, hands them the raw file, lets them write any content, and spends model tokens on their behalf without counting. A customer author gets none of that trust by default, and each place the tooling currently extends it becomes a work item.

Where to build it matters as much as what to build. The Scenario Editor is a stated-temporary tool — Learning Studio grows its own scenario authoring in roughly six months. So the durable investments (login and tenancy, API storage, the safety floor, metering, role-gated endpoints) belong in Learning Studio and the V1 engine, where they outlive the editor. Changes to the editor itself should stay skin-deep.

1The prompt preview becomes a permission — and prompt assembly moves server-side

The prompt layer is the secret sauce, and it currently leaks in two places. The editor's Compiled prompt pane shows the full composed system prompt with authored-versus-template highlighting. And the V1 engine's POST /authoring/preview-prompt endpoint returns the same thing — the real composed prompt plus provenance spans — to any caller.

Hiding the pane is not the fix. The editor is a static page: it composes the prompt in the browser, which means the template text ships in the JavaScript to every visitor whether the pane renders or not. The requirement is stronger: the customer-facing build never receives template text at all. Prompt assembly happens only on the server — which is already how the V1 engine works (templates live in Langfuse and are composed at runtime) — and preview-prompt gets role-gated so only internal authors can call it.

  • The line is clean, which helps. The scenario file holds only what the author wrote; no template text ever enters it. The format needs no change to keep the secret — only the tooling around it does.
  • Internal authors keep the pane. It stays the best debugging tool the K&A team has. It becomes a role, not a feature to delete.

2Login, tenancy, and roles — the "no login in the editor" decision inverts

The Learning Studio integration deliberately has no login in the editor: it is a static page with no server, and Learning Studio owns storage. That was the right call for internal LXDs and it stops working the moment an external author exists. The session has to know who is authoring and which organization they belong to, because everything downstream scopes by it: which scenarios they can see, which templates they can start from, which media they can use, and whose model budget their preview spends.

  • Learning Studio is the natural identity host. The editor already launches from it with ?lo=&title=; the launch handoff grows a session token instead of the editor growing its own accounts.
  • Two roles minimum. Internal author (full surface, prompt pane, every field) and customer author (reduced surface, no prompt visibility). More granular customer roles can wait.
  • The locked-scenario policy generalizes. The V1 engine already has a read-and-copy-only list for its five flagship scenarios. That becomes the model for a Vector-owned template library: customers duplicate, never edit the original.

3Retire the download/upload seam — customers save through the API

Scenario files currently move between the editor and Learning Studio by download and upload. Chosen as the simple, temporary seam for internal use, it fails for customers twice over: it is a support cliff (files hand-edited, renamed, uploaded into the wrong record), and it puts the raw document in customer hands, inviting edits the strict v4 schema will reject with errors no customer should have to read.

The replacement already exists: the V1 engine's authoring API — get, save, copy, with atomic writes, the same validation gate as a production save, and structured failure messages. The customer-facing editor saves directly through it under the author's session. Server-side validation stops being a nicety and becomes non-negotiable, because every customer save is untrusted input.

4A safety floor the author cannot remove

The prompt crosswalk found that the V1 engine has no unconditional safety floor — every conduct rule the characters follow is authored, per character. That is tolerable when every author is trained staff. It is not tolerable when external authors write the character behavior, scene text, and coaching guidance that get compiled into model prompts.

  • A non-removable conduct floor in the fixed scaffold, beneath anything authored. This was already proposed as extensions proposal #1; customer authoring upgrades it from improvement to prerequisite.
  • Authored text treated as data, not instructions. The scaffold needs hardening so a scenario field cannot smuggle directives to the model — the same discipline as any prompt-injection surface.
  • A moderation gate at save or publish for content that should never reach learners regardless of how well the model behaves at runtime.

5Meter the model spend

The AI-assisted parts of authoring — the wizard that drafts a scenario, the say/do splitter, live preview — all spend model tokens, today through an open proxy with no notion of who is asking. Customer authoring needs per-tenant quotas, rate limits, and abuse handling before any of those features are exposed, plus a product decision about which generation features customers get at all.

6A smaller authoring surface, with quality guardrails

The full field surface — calibration tiers, turn budgets, per-character guardrails, level blocks — is craft-heavy even for internal LXDs. Customers need the wizard-and-template path as the front door, with most of the advanced controls held at locked defaults, and validation messages rewritten in plain language (the API's structured schema, cross-field, and lint failures are the right raw material).

The deeper reason is quality, not simplicity. A badly authored scenario makes the coach misbehave in front of that customer's learners, and the customer will read that as the product failing, not their authoring. Lint-level quality checks — and possibly an AI review pass before publish — protect the experience from its own authors.

7Preview and publish without exposure

The one-engine decision stands: the prototypes are a design reference, and real fidelity comes only from the V1 engine. Customers arguably need preview more than internal LXDs do — they cannot be told "trust us." The safe shape is two-part: the editor's deterministic structure walkthrough (no model, no prompts), plus a play-it-as-a-learner preview against the real engine, where the composed prompt never appears. That keeps a strict split between the learner-view preview (customer-safe) and the prompt view (internal only).

Publishing is the open product question: does a customer-authored scenario reach their learners with no Vector review at all? Draft, review, and publish states live in Learning Studio either way — the decision is whether "review" ever involves Vector, and for which content categories.

What doesn't change

  • One document per scenario, holding only authored content. The format already keeps the secret; the tooling just has to stop volunteering it.
  • The v4 schema stays strict and the authoring service stays the single validator. Untrusted authors make both more valuable, not less.
  • Learning Studio owns storage, versioning, and publish. Customer authoring adds roles and workflow states to that ownership; it does not move it.
  • No second engine. Customer preview rides the V1 engine, same as internal preview.

Open questions

  • One editor build or two? A static page cannot keep secrets from its own users, so internal-only capability has to be absent from the customer build, not hidden behind a flag. Whether that means two builds of the current editor or waiting for Learning Studio's native authoring depends on the timeline.
  • Does the six-month horizon change the order? If Learning Studio's own authoring is real and near, the platform work (items 1–5) is worth starting now and the editor-surface work (item 6) may be better spent on the native tool.
  • Which customers, and how many knobs? A pilot with a few high-touch customers tolerates a rougher surface and manual review; self-serve at scale needs everything on this page.
