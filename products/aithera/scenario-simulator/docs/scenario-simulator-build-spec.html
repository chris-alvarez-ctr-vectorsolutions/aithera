Scenario Simulator · End-to-end Flow

Build & Authoring Specification

A technical view of the scenario flow: what each phase does, what must be authored, what is generated at runtime, and the schema and platform we build once so scenarios scale. The middle phase — the interaction layer — takes one of several modes; this doc uses the conversation (Roleplay) mode as its worked example, and the Interaction Layer companion covers all seven types (four core modes + three specialized engines) in depth.

Status — Draft for product + engineering Worked example — “Kendra’s Room” (Roleplay mode) Companion — The Interaction Layer
Design history — not a current contract

Written before the POC V4 retrofit. Its central assumption — that a scenario declares its type as a field — is the one thing V4 changed: there is no type field, and the scenario types survive as authoring templates. Read the phase anatomy and the authoring/generated split as still current; read “type” as “template”. The current record is the Scenario CML v4 alignment notes, and the open decisions are routed by owner in its Who Decides What section.

1

Flow anatomy

The simulator is a single learning object (LO) with a defined entry and exit. Internally it runs three parts: a context intro, the interaction layer (a repeating Engage → React → Coach loop), and a debrief & close. Every screen in the flow is one of two kinds — and that distinction is the organizing principle of this whole document.

Authored — written by a content author, fixed at design time Generated — produced by the model at runtime Generated within authored guardrails

The key insight for planning: nothing pink is free. Every generated moment depends on authored inputs — a character card, a rubric, a guardrail set. The authoring work doesn’t disappear when AI produces the words; it moves upstream into structured configuration.

2

Phase — Scenario Context

2

Orient and prime (Enter)

The learner sees the scenario title, absorbs the situation in one chosen intro modality, and answers an opening reflection. The reflection is drawn out in-context — the coach may probe once — but it never blocks: practice begins regardless. The only variation here is the intro modality, chosen once up front.

Authored per scenario

Title & framing copyScenario name plus 1–2 sentences setting learner expectations (“Kendra’s room”).
Intro modality (one of five)The situation set in one chosen modality: video (asset + captions), story-highlight (rich text with highlight anchors), narrated audio, plain reading, or none. Chosen once, up front, and delivered by the shared SceneContext player.
Opening reflection promptThe open question the coach asks before the scene.
Reflection focusThe ideas the coach should draw out (e.g. name the root cause; name the safety risk). Surfaced in-context — never a pass/fail gate.

Generated at runtime

Reflection feedbackThe coach responds to the learner’s reflection and, if a focus idea is missing, probes for it once — then moves into the scene regardless.
Opening scene framingThe coach’s first in-scene line, grounded in the authored setup and opening image so the learner never lands on an empty stage.

Schema — context block (per scenario)

// scenario.context
{
  "framing": { "title": "Kendra's Room", "courseContext": "…" },
  "intro": {
    "type": "video",           // video | story | audio | reading | none — chosen once
    "video": { "scenes": [{ "src", "caption" }] },
    "story": { "paragraphs": [], "keyMoments": [{ "phrase", "label" }] }
  },
  "openingQuestion": "What do you want this conversation to do?",
  "reflectionFocus": ["names the root cause", "names the safety risk"]  // drawn out in-context — not a gate
}
→Ties to the interaction layer: Enter → the loop is an unconditional handoff — the reflection primes the learner but never blocks. What carries forward is the coach’s read of the reflection, folded into the first turn.
3

Phase — The interaction layer (Roleplay mode)

3

The loop: Engage → React → Coach

In the conversation (Roleplay) mode, the learner speaks one line in character (Engage), the character responds once (React), and the coach reads the exchange and nudges (Coach) — overlaid on the scene, not a separate mode. That loop runs ~4–6 turns; the Gate is the hinge that runs it again or advances. Other modes fill the same loop differently (see the companion).

Authored per scenario

Character cardWho the character is — authored as setup (backstory + what they know), a reactions map (when → then), and styleNotes (voice). Every generated character line depends on it — the most leverage-heavy artifact.
Assessment dimensions2–4 dimensions, each with what strong and weak look like. Scored silently — they steer the character’s reactions and aim the coach at the learner’s weakest dimension. Never shown to the learner as a rubric.
Misconceptions & pacingCommon wrong beliefs to watch for, plus pacing (target scene lines, duration) that tunes the loop length.
Response promptsThe authored coach nudge (“Who could you connect her to?”). Steers without scripting.
The gateThe one move the scene won’t resolve without (gate.requirement): its two-nudge cap and fallback. Hard or soft is the author’s choice.

Generated at runtime

Character response (1× per turn)Single-shot, not open chat — the character replies once to the learner’s move, with an emotional state, constrained by the character card. This is what keeps the scenario authorable and predictable.
Coach feedback & nudge (per turn)Generated against the dimensions, in the coach’s configured voice (see §5), aimed at the weakest dimension — then the Gate decides whether to loop again.

Schema — character card + scoring & gate

// character card — authored as three fields, not one object
{
  "characterName": "Kendra",
  "setup": "backstory + what the character knows",
  "reactions": [{ "when": "learner shows empathy", "then": "softens" }],
  "styleNotes": "guarded, dry humor, short sentences"
}

// scoring + gate — the loop is model-driven turns, not an authored beat list
{
  "pacing": { "sceneLines": "4-6" },
  "dimensions": [{ "name", "strong", "weak" }],   // silent rubric
  "gate": { "requirement": "connect Kendra to real help", "nudgeOpen", "nudgeConcrete", "fallback" }
}
→Ties to Debrief: the loop persists a structured record per turn (learner move, character response, dimension results) — not just chat text — and hands that summary to the evaluation engine (§4).
4

Phase — Debrief & close

4

Analyze, summarize, hand off

After the final turn, the coach signals a shift (“Analyzing…”), then a separate evaluation engine — distinct from the in-scene coach — scores the session against the authored dimensions and produces the wrap-up: strengths, growth areas, and a closing. This is where the scenario emits its proficiency record, so it is the most guardrail-dense phase.

Authored per scenario

Evaluation rubricThe dimensions this scenario measures and what strong and weak look like. Strengths and growth are generated only within this frame — the author decides what the scenario measures. (Teach-Back scores coverage instead; the output shape is the mode’s.)
Strengths / growth guardrailsConstraints on the generated summaries: evidence must quote the learner’s own moves, max 3 items each, growth framed as next steps, prohibited framings.
Playbook & resources (optional)Guaranteed takeaways, identical for every learner, plus domain-specific resources — authored, never generated. Scenario-specific (e.g. Kendra’s substance-use + crisis support).

Generated at runtime

Results surfaceStrengths & growth areas (Roleplay), or a coverage score (Teach-Back) — evidence-grounded, guardrail-bounded, returned as typed JSON, not prose.
Proficiency recordThe structured exit signal — dimensions × evidence, or a score — that makes the scenario composable downstream.
Coach closingPersonalized send-off into the authored closing.

Schema — debrief block

// scenario.debrief
{
  "dimensions": ["empathy", "open questioning", "referral to support"],
  "strengths": { "max": 3, "guardrails": ["cite learner's actual words"] },
  "growthAreas": { "max": 3, "guardrails": ["frame as a next step", "tie to a dimension"] },
  "closing": { "template": "scaffold with {generated} slots", "cta": "Continue" },
  "exit": { "nextLO": "lo-ref", "emitSignal": "proficiency-record" }
}
→Ties to the LO sequence: the exit emits a structured proficiency record (dimensions × evidence, or a coverage score), which is what makes this scenario a composable LO rather than a dead-end activity — and what feeds the broader provable-proficiency signal downstream.
5

Cross-cutting: built once, reused everywhere

Several artifacts sit outside any single scenario. These are the platform layer — they get built and tuned once, and every scenario inherits them. This is where scale actually comes from.

Configuration (authored once, org-level)

Coach configThe coach’s persona, tone, feedback shape (e.g., “two sentences + one question”), coaching framework, and safety rules. One coach voice across all scenarios; overridable per scenario only if we ever need it.
Compiled prompt + locked guardrailsEach mode’s compile() turns the authored fields into the system prompt. The conversation mode compiles one prompt; inside it sit four locked guardrail sections (output contract, off-script handling, safety floor, grounding) that authors can’t edit. Prompt count is per-mode — Teach-Back compiles three.

Engineering (built once)

Prompt compiler + mode registryEach mode registers with the studio; its compile() assembles the prompt from authored fields. There is no runtime interpreter — the model carries turn state via the JSON contract, and the page orchestrates I/O across Enter → loop → Gate → Exit.
Typed message schema + worker proxyExtends the established pattern (typed JSON messages, Cloudflare Worker proxy for model calls) already proven in the conversation-practice module. All generated moments return structured output validated against the schema.
Transcript & signal storePersists the structured per-turn record and emits the exit proficiency signal.
Authoring validationSchema validation + a lint pass (every scenario has dimensions, the gate has a fallback, the character card has style notes) so authored scenarios fail fast, not in front of a learner.

Settled decisions

Four choices that shape the schema, now settled: (1) the type set — four core modes (Roleplay, Guided Arc (a phased reflection → Practice⇄Learn arc, ending in an optional live scene), Observe/React, Teach-Back) plus three specialized engines (Scene-Sweep, Branching Arc, Ensemble Arc); new pedagogies are designed and built against the same contract. (2) Gating is the author’s choice per scenario — hard (blocking) or soft (nudge-then-advance), and a scenario may use both. (3) Prompt count is decided by the platform, not the author — one compiled prompt where that suffices, more where a mode needs them (Teach-Back: three). (4) The proficiency record is produced by a separate evaluation engine that scores summarized progress against the authored rubric — the contract that makes these scenarios legible downstream.
