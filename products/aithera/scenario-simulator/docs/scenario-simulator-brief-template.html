The Scenario Brief — a PowerPoint template the editor can read

The K&A team's 32-slide POC deck, redesigned as the canonical input to the Scenario Editor. It keeps PowerPoint — the versioning, the comments, the collaboration — and drops everything the editor, the wizard, or the player now does for you. Nine slides for a three-step scenario. Every field is a placeholder, so Outline view exports the whole brief and nothing else.

The one-sentence version

The old deck was about a quarter input and three quarters output. The editor and wizard need roughly nine slides' worth of what is in it; the other twenty-odd are the AI's job (the full-dialogue examples), the engine's job (the eight transition screens with engineering notes), or presentation for the working session. The brief keeps the quarter, gives every field a home the editor recognises, and adds the handful of things the old deck never carried — a declared cast, a per-step right answer?, must-knows separate from the ideal response, and external authorities separate from internal slide numbers.

What "canonical input" means here. The brief is not a second copy of the scenario to keep in sync with the editor. It is the step before the editor: the SME-owned facts, locked lines and grading logic, in the order the wizard's interview asks for them. The wizard drafts everything else, and the editor is where the draft is refined and validated. Nothing flows back into the deck.

Why the phase map is not a slide

Slide 32 was the most useful slide in the old deck — and it is also a second copy of every step's mode, turns, locked line and button, kept in sync by hand. A canonical input should hold each fact once. So the spine lives in two places that don't overlap: the Steps field on THE BRIEF (order and mode) and the STEP slides (everything else). The phase-map view is what the editor's step rail already renders, and what a future review-deck export would print.

Drafted, never authored

These v4 fields have no slot in the brief on purpose. The wizard writes them, the editor shows them, and a reviewer changes them there if they need changing: every id, button label and input placeholder; each practice's and debrief's model-facing purpose phrasing; the debrief's final_word and probe; the scene world's canon.facts; a character's baseline and emotion_hint; partner_label and help_turns. The dev conversation already established that several of these were being filled "to satisfy a schema slot, not SME-authored" — the brief simply stops asking humans to write them.

4Five rules that make it an input

  • Every field is a placeholder — never a table, never a text box. PowerPoint's Outline view exports title and body placeholders only. That one rule is what makes copy-out lossless, so the layouts carry the decoration and the slides carry only fields. The footer on every slide says so.
  • Keep the label line. Each field's first line is its label, pre-filled in the placeholder. It is exported with the value and it is how the importer knows what it is reading. Duplicate a STEP slide rather than inserting one from the layout gallery — a fresh slide from the gallery arrives with prompt text, not labels.
  • Two registers, marked on the slide. A field tagged verbatim is what the learner reads, word for word: the narrative, the opening question, each step's opener, the closing summary. Everything else is guidance for the coach, written as imperatives.
  • No engine notes. Triggers, input types, partner labels and on-submit behavior are fixed by the player; the v4 lint rejects text about the AI or the interface anyway. If it would have gone in a "Design notes for engineering" box, it doesn't go in the brief.
  • Sets A and B and second-turn dialogue are output. The old deck asked a human to write four exchanges per tier per step. The format stores one; the wizard drafts it; the EXAMPLES slide exists only for the case where the SME has a specific exchange they want to lock.

Parsing rules, for whoever builds the importer:

  • Slide titles are section keys. SCENARIO BRIEF, THE BRIEF, THE SITUATION, THE TEACHING, THE OPENING, STEP N · <label>, STEP N · EXAMPLES, THE CLOSE, SOURCE MATERIAL. Anything else is ignored. A missing THE OPENING means no warm-up.
  • Uppercase label lines are field keys; the lines until the next label are the value. Tier panels nest one level: the tier name, then Look for: / Respond: / Scene moves (roleplay only): (or Learner: / Reply: on an EXAMPLES slide).
  • List fields split on line breaks, and Debrief lands also on · . A step line splits on its first colon: mode, then description — the same rule the wizard's step field uses today, so coach:, roleplay:, observe: and their synonyms all resolve.
  • Cast lines split on spaced dashes: name, role, driver, then anything after is the character's guardrails.
  • Verbatim fields land as-is, quotes stripped. Every other field is interview material the wizard drafts from.
Where the plumbing is today. The wizard's brief screen already has a paste-anything box with a file drop and a hint that says to copy the outline from PowerPoint — but that text reaches the model only as source material to mine. The next step is a small deterministic parser in studio-v2-v4-universal-wizard.js that recognises the labels above and pre-fills the interview fields directly, so the AI drafts only what the brief left blank and verbatim fields land untouched. No build step, no file parsing — just the labels. After that, a .pptx drop that reads placeholders by machine key would make the labels optional.

6Open decisions

  • Media. The deck wants the setup delivered as video; the v4 narrative is text. Where a video reference lives — a landing asset, or an observe exhibit — is a format question, not a template one. The brief has no media field until it is answered.
  • Container. PowerPoint works if the placeholder discipline holds. A Word or Google Docs rendering of the same field list would export cleaner (headings and paragraphs are the outline) and keeps comments and versioning too. The field list is the template; the file format is a rendering of it, and the generator could emit either.
  • Verify the export rule in real PowerPoint once. Outline view exporting all body placeholders on a custom layout is documented PowerPoint behavior, but this machine has no PowerPoint, so the decks were checked structurally and with a stand-in renderer. One round trip — fill a step, View → Outline, paste — settles it.
  • A review-deck export. The part of the old deck reviewers liked was Version B. Generating it from the drafted document (one slide per step, the example exchange per tier) would give stakeholders the format they know without anyone hand-writing dialogue again. Worth a ticket once the importer exists.
  • Source references. Two fields, deliberately: the close ships external authorities only, and the team still needs slide-number traceability. The old deck mixed them.

How it was built

tools/build-scenario-brief.py turns one field list into both decks with python-pptx: nine custom slide layouts, each field a real body placeholder with a fixed index, a machine-readable shape name, a list style (so typed text inherits the right size and no bullets) and prompt text; panels and helper text live on the layout so they can't be edited or exported. tools/render-pptx-html.py draws any such deck to HTML for eyeballing — the previews above — because there is no Office here. The generator also sizes the worked example's text by arithmetic and reports any field near capacity, so a longer scenario that overflows a panel is a rebuild with shorter copy, not a mystery.
