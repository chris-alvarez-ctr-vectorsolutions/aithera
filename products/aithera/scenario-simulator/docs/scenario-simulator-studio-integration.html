The Scenario Editor is a temporary tool. In about six months Learning Studio will have its own scenario authoring, so this integration should stay simple and easy to replace.

The approach

  • The editor stays its own page. Learning Studio opens it in a new window with the scenario's ID and title in the URL.
  • The scenario file moves by download and upload. The editor already handles both directions.
  • Learning Studio stores one file per scenario. The editor file holds everything the LXD authored, and it is the file the player loads.
  • Learning Studio's scenario ID goes in the document's implementation_id field, so the file always knows which scenario it belongs to.
  • No login in the editor. It has no server and stores nothing itself. Uploading, versioning and deleting all happen in Learning Studio.
Why not an iframe. The editor keeps work in progress in browser storage (localStorage), and browsers block or isolate that storage inside an iframe. Since it holds the only copy of an unsaved scenario, an LXD could lose work. We have already seen a smaller version of this problem: window.confirm() returns false without ever prompting inside an embedded browser, which made the editor's Delete button do nothing.

The Learning Object

In Learning Studio, a Learning Object is the record that holds one piece of content. It has an ID, a title, a status and a modified date, and it is what shows up in the content lists. Scenes, questions and citations all live inside one Learning Object.

A scenario works the same way. It gets its own Learning Object, and the exported scenario JSON is that object's content, which is where the .lo.json file extension comes from. Everywhere below, the thing Learning Studio creates, versions, stores files in and hands a file back from is that Learning Object.

Learning Studio does the work here. The editor never sees the Learning Object. It only receives the ID and title in the URL, and writes the ID into the scenario file so the file can be matched back to the right record later.

The flow

One file

Learning Studio stores and exchanges a single file per scenario: the one the editor produces. It holds everything the LXD authored, it is what comes back when someone edits, and it is what the player loads.

The editor can also produce a trimmed copy with its unsupported fields removed. That copy is useful for handing the dev team a strictly conformant sample, but it is not part of this flow and Learning Studio does not store it.

Two fields in that file are ahead of the format: the prior-scenario context that tells the coach what ran before, and the marker saying a practice has one right answer. The v4 schema refuses fields it does not recognise, so the production engine will not load a scenario carrying them until v4 adds them. That is a known dependency rather than a problem to design around — keeping two files in sync on both sides would be permanent complexity in exchange for a gap that should close.

New scenario

  1. The LXD taps New Scenario and enters a title.
  2. Learning Studio creates the Learning Object and generates the scenario ID.
  3. The Scenario Manager lists it as Draft.
  4. Learning Studio opens the editor at ?lo=<id>&title=<title>. The editor fills in the title, sets the ID and starts the wizard.

Save and update

  1. The LXD exports the scenario file.
  2. The LXD uploads it.
  3. Learning Studio validates the upload and compares its ID and title against the Learning Object. Use the existing authoring service to validate rather than writing a second validator.
  4. Learning Studio saves it as a new version and updates the status and date.

Edit an existing scenario

  1. The LXD picks a scenario and chooses Edit or Duplicate.
  2. Learning Studio sends back the same file it stored.
  3. In the editor, the LXD chooses Open an existing scenario, loads the file, edits it, and exports again.

Scenario IDs

Put Learning Studio's scenario ID in the document's implementation_id field. The field already exists in the v4 format, and its description in the editor already reads "how the surrounding content system identifies this implementation." Storing the ID there means the file knows which Learning Object it belongs to even after it has been emailed or downloaded onto another machine.

  • Learning Studio generates the ID once, when it creates the Learning Object.
  • Do not rebuild the ID from the title. The wizard currently falls back to a slug of the title, so renaming a scenario can change the ID the engine uses for routing. Remove that fallback.
  • Make the field read-only when Learning Studio supplied the ID. It is editable text today, and an LXD who types over it breaks the link to the Learning Object with no warning.
  • Duplicating a scenario needs a new ID, otherwise two Learning Objects share one routing key.
  • Change the download filenames in the same update. Filenames are built from implementation_id first, so an ID like a GUID would make every download unreadable. Use content.title instead and fall back to the ID.

Images

In the v4 format, media is { type, src, alt } and src is a plain string. The format has no field for image data, so the file can only hold a reference. Learning Studio's media library has to store the actual image.

What each side builds

Scenario Editor

  • Read ?lo= and ?title= on load. Fill in the title, set the ID, and make the ID read-only.
  • Stop rebuilding implementation_id from the title.
  • Build download filenames from content.title.
  • Store local drafts under the lo ID, so reopening a scenario resumes the right draft.
  • Nothing new for the one-file flow — the export the LXD already uses is the file Learning Studio wants.

Learning Studio

  • Create the Learning Object and generate the ID on New Scenario, then open the editor with both.
  • Store the uploaded file, versioned.
  • Send back the same file when someone edits a scenario.
  • Validate on upload using the authoring service, and show its failures[] list.
  • Compare the ID and title on upload, following the table above.
  • Make the asset uploader and picker reachable from the Scenario Manager.
  • Generate a new ID when a scenario is duplicated.

Questions for the dev team

  • Can implementation_id be any format? The schema only requires a non-empty string, but all 11 production documents use readable slugs, and the loader has read a scenario ID from the filename in the past. We need to know whether anything downstream expects a particular format before Learning Studio picks one.
  • Can the Learning Studio backend call the validation endpoint? If not, we need the v4 JSON Schema as a file so Studio can validate on its own.
  • Does an API already exist for creating a Learning Object? And is one scenario exactly one Learning Object, or does a scenario sit inside a larger one alongside other content? Everything here assumes one scenario per Learning Object.
  • Do image URLs work without a login?
  • When can v4 accept the two fields the editor authors? Prior-scenario context was approved on 18 August and the format still has no field for it. One file depends on this landing — otherwise the options are relaxing the schema or dropping the two features.
