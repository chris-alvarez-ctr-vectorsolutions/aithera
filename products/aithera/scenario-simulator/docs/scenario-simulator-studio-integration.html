Integration strategy

  • The Scenario Editor runs in an iframe inside the Learning Studio page. Learning Studio's own window is the wrapper around it.
  • The wrapper owns Save, Publish and Preview. Those controls live in the main window. The editor hides its own header and primary buttons when embedded, so there is one set of controls, not two.
  • The two sides talk over events. The wrapper asks the editor for the current document and the editor hands it back. The LXD never downloads or uploads a file.
  • Drafts persist to localStorage on the Learning Studio origin — the main window's own storage, so it is first-party and not subject to the restrictions that apply to storage inside an iframe.
  • Publish is a wrapper action and means the scenario goes live to learners. There is no separate draft record: the local copy is the draft.
  • The wrapper handles images. It uploads to S3, gets a URL back, and that URL is what gets saved as the media reference in the scenario.
  • No login in the editor, and no direct contact with Learning Studio's backend. Everything it needs arrives from the wrapper.
Already true of the editor: it has no native browser dialogs left. Every confirm and prompt was replaced with an in-page dialog, precisely because a native one is suppressed inside an embedded browser and returns false without asking. One alert() survives, in the storage-quota path in studio-engine.js, and it should go the same way.

How the pieces sit

Everything happens in one browser window. The editor is inside it, and talks to nothing but the wrapper — that is the property that makes the rest of this simple.

The one rule worth protecting: every outward connection starts at the wrapper. If the editor ever calls Learning Studio's backend or S3 directly, it needs credentials, and the reason it can stay a throwaway tool disappears.

The LO wrapper

In Learning Studio, a Learning Object (LO) is the record that holds one piece of content. It has an ID, a title, a status and a modified date, and it is what shows up in the content lists. Scenes, questions and citations all live inside one Learning Object.

A scenario works the same way. It gets its own Learning Object, and the scenario JSON is that object's content, which is where the .lo.json file extension comes from.

The Learning Studio backend owns it. Creating it, generating its ID and publishing it are backend work. The main window owns the working copy — the draft in localStorage, and the controls that act on it.

Step by step

Every step names the part of the system that performs it.

New scenario

  1. In Learning Studio, the LXD taps Create New Scenario and enters a title.
  2. The Learning Studio backend creates a draft Learning Object and generates its scenario ID.
  3. The main window opens the authoring view with the editor embedded, passing in the ID and title.
  4. In the iframe, the editor sets implementation_id to the ID, fills in the title, and offers its starting points — draft with AI, start from a template, or open an existing scenario.

Save

  1. In Learning Studio, the LXD presses Save in the main window.
  2. The main window asks the editor for the current document.
  3. The iframe returns it.
  4. The main window writes it to localStorage on its own origin. This is the draft, and it is the only copy until publish.

Preview

  1. In Learning Studio, the LXD presses Preview.
  2. The main window takes the latest saved document and hands it to the production engine.
  3. The scenario runs on the real engine, not on a preview built into the editor.

Publish

  1. In Learning Studio, the LXD presses Publish.
  2. The main window sends the saved document to the backend.
  3. The Learning Studio backend validates it and stores it against the Learning Object. It should call the existing authoring service to validate rather than reimplementing the rules.
  4. The scenario is live to learners.

Validate before publish, not after

The v4 schema refuses fields it does not recognise, so an invalid document fails to load rather than degrading. The editor already checks a document against the production loader's rules, so the wrapper can surface that result on Save and stop a bad Publish before it reaches learners.

Edit an existing scenario

  1. In Learning Studio, the LXD opens a scenario from the Scenario Manager.
  2. The main window loads the draft from localStorage, or the published document from the backend if there is no local draft.
  3. The main window sends that document into the iframe.
  4. In the iframe, the editor renders it and the LXD edits. Saving follows Save above.

Other considerations

Draft durability

With no draft record on the server, the draft lives in one browser profile on one machine. Clearing site data, switching browsers or losing the laptop loses the work, and two authors cannot pass a half-finished scenario between them.

The sharper version: publish is the only thing that persists anywhere but that browser, and publish means live to learners. So an LXD who wants their work stored somewhere durable has to make it live, and one who does not has to trust localStorage to survive.

The cheap fix, if it becomes a problem: have the wrapper also send the draft to the backend on Save, stored against the Learning Object as a draft and not served to learners. The wrapper already holds the document at that moment, so it is a place to put it rather than new plumbing. Worth deciding deliberately rather than discovering it when someone loses a day of authoring.

Creating a scenario

Splitting the question in two makes it easier to answer:

  • Creating the Learning Object — the record, its ID and its title. Already the wrapper's, and already built in the flow above.
  • Choosing what the scenario starts as — blank, one of the templates, or AI-drafted. This is authoring, and it should stay in the iframe.

The second one belongs to the editor because that is where the knowledge lives. The template gallery reads the scenario-type registry, and each template is a complete, valid v4 document with the teaching content left blank. For the wrapper to offer that picker it would have to know which templates exist and how to produce a valid skeleton for each — duplicating the editor's job, in a tool meant to be replaced.

So: yes, creation is in scope, and it is the editor's half that matters. When the header and primary buttons are hidden for embedding, the New scenario panel must not go with them — it is not a call to action, it is the entry point. The editor already opens it by itself when it boots with an empty document.

Scenario IDs

The scenario ID the backend generates goes into the document's implementation_id field. The field already exists in v4, and its description in the editor already reads "how the surrounding content system identifies this implementation."

  • The backend generates it once, when it creates the Learning Object. Nothing else ever generates one.
  • In the editor, do not rebuild the ID from the title. The wizard currently falls back to a slug of the title, so renaming a scenario can change the ID the engine routes on. Remove that fallback.
  • In the editor, make the field read-only when the wrapper supplied the ID. It is editable text today.
  • Duplicating a scenario needs a new ID, generated by the backend like any other, or two Learning Objects share one routing key.

Images

In the v4 format, media is { type, src, alt } and src is a plain string. The format has no field for image data, so the scenario can only hold a reference — which is exactly what the wrapper's S3 flow provides.

  • The wrapper uploads to S3 and gets a URL. That URL is saved as the media reference in the scenario.
  • This also removes the storage problem. Embedding an image as base64 could approach the browser's storage limit on its own; a URL costs a few dozen bytes.
  • Nothing to author beyond the reference. The v4 observe practice has no hotspot coordinates — its rubric is text based — so the LXD never places markers on an image.
  • Still to decide: whether the S3 URL resolves without a Learning Studio session. If it does not, images will not render in the editor or in a preview.

Reuse and versions

A scenario reaches a learner by being added to a course as a knowledge-check question type, which means one scenario can be referenced from several places. Publish settles what a version is; it does not settle what happens to the references.

  • What appears in the scenario picker? Published scenarios only, presumably, since a draft exists only in one author's browser.
  • What happens to courses already referencing a scenario when it is published again? Either they follow the latest version, or they stay pinned to the one they were attached to.

Nothing goes wrong here until a scenario is reused, which is what makes it easy to miss. Following the latest is simpler and fixes a typo everywhere at once. Pinning is safer for compliance content, where an approved scenario should not change under a course without someone deciding it should — and these scenarios cover harassment, bullying and hazmat. Suggestion: pin the reference and give the course an explicit update action. A product call, not a technical one.

Updates needed

Scenario Editor

  • An embedded mode that hides the header and primary buttons, and keeps the New scenario panel.
  • Receive a document from the wrapper and render it.
  • Return the current document when the wrapper asks.
  • Stop writing its own localStorage drafts when embedded, so there is one working copy rather than two that can diverge.
  • Replace the last alert() in studio-engine.js with an in-page message.
  • Set implementation_id from the wrapper and make it read-only.
  • Stop rebuilding implementation_id from the title.
  • Accept an image URL as a media reference from the wrapper's picker.

Learning Studio

  • Frontend — embed the editor and define the event contract in both directions.
  • Frontend — Save, Publish and Preview controls in the main window.
  • Frontend — write and read the draft in localStorage.
  • Frontend — surface validation results on Save, and block a failing Publish.
  • Frontend — image picker that uploads to S3 and returns the URL to the editor.
  • Backend — create the Learning Object and generate its ID.
  • Backend — validate on publish via the authoring service.
  • Backend — publish and unpublish, and store the published document.
  • Backend — generate a new ID when a scenario is duplicated.

Open questions

  • The event contract. Which messages exist, who initiates each, and what happens when the editor does not answer. Worth writing down before either side builds against it.
  • Does the wrapper need to know the document changed? If Save is the only trigger, an LXD can close the tab on unsaved work. An "editor says it is dirty" event would let the wrapper warn.
  • Draft durability — server-side draft on Save, or accept one browser as the only copy.
  • Do S3 URLs resolve without a Learning Studio session? This decides whether images render in the editor and in previews.
  • Reuse — what the scenario picker lists, and whether references pin to a version.
  • Can implementation_id be any format? The schema wants a non-empty string, but all eleven production documents use readable slugs and the loader has read a scenario ID from a filename in the past. Worth confirming nothing downstream expects a shape before the backend picks one.
