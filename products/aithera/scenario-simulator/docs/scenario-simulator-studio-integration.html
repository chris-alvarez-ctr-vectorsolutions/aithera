Integration strategy

  • The Scenario Editor stays its own page, on its own domain. The Learning Studio frontend opens it in a new browser tab with the scenario's ID and title in the URL.
  • The scenario file moves between the two systems as a download and an upload, both done by the LXD in their own browser. Nothing is transferred system to system.
  • The Learning Studio backend stores one file per scenario and versions it. That file holds everything the LXD authored, and it is the file the player loads.
  • The scenario ID the Learning Studio backend generates goes into the document's implementation_id field, so the file always knows which scenario it belongs to.
  • No login in the Scenario Editor. It has no server of its own and stores nothing but browser-local drafts. Uploading, versioning and deleting all happen in Learning Studio, which already has authentication.
Why not an iframe. The editor keeps work in progress in browser storage (localStorage), and browsers block or isolate that storage inside an iframe. Since it holds the only copy of an unsaved scenario, an LXD could lose work. We have already seen a smaller version of this problem: window.confirm() returns false without ever prompting inside an embedded browser, which made the editor's Delete button do nothing.

The LO wrapper

In Learning Studio, a Learning Object (LO) is the record that holds one piece of content. It has an ID, a title, a status and a modified date, and it is what shows up in the content lists. Scenes, questions and citations all live inside one Learning Object.

A scenario works the same way. It gets its own Learning Object, and the exported scenario JSON is that object's content, which is where the .lo.json file extension comes from. Everywhere below, the thing that gets created, versioned, stored into and handed back from is that Learning Object.

The Learning Studio backend owns it. Creating it, generating its ID, storing the uploaded file against it and keeping its version history are all backend work. The Learning Studio frontend shows it in the Scenario Manager and provides the upload and download controls.

The Scenario Editor never sees the Learning Object. It receives only the ID and title, in the URL, and writes the ID into the scenario file so the file can be matched back to the right record later. It has no access to Learning Studio's storage or API.

The flow

Step by step

The same three phases as the diagram above, spelled out. Every step names the system that performs it.

New scenario

  1. In Learning Studio (frontend) the LXD taps New Scenario and enters a title.
  2. The Learning Studio backend creates the Learning Object and generates its scenario ID.
  3. The Learning Studio frontend lists the new Learning Object in the Scenario Manager with a status of Draft.
  4. The Learning Studio frontend opens the Scenario Editor in a new browser tab at ?lo=<id>&title=<title>.
  5. In the Scenario Editor, the page reads those two values from the URL, fills in the title, sets implementation_id to the ID, and starts the new-scenario wizard.

Save and update

  1. In the Scenario Editor, the LXD exports the scenario file. It downloads to their own machine.
  2. In Learning Studio (frontend) the LXD opens the scenario's Learning Object and uploads that file to it.
  3. The Learning Studio backend validates the upload and compares its ID and title against the Learning Object it was uploaded to. It should call the existing authoring service to validate rather than reimplementing the rules.
  4. The Learning Studio backend saves the file as a new version of the Learning Object, and the frontend updates the status and modified date in the list.

Checking the upload

The comparison in step 3, case by case.

What the backend finds on uploadWhat it does
ID and title both matchSave it. No prompt needed.
ID matches, title differsOffer to update the Learning Object title. LXDs often improve the title while authoring.
ID does not matchWarn and show both IDs, with Cancel as the default. This usually means the wrong file went into the wrong Learning Object.
No ID in the fileOffer to assign the Learning Object's ID. This covers scenarios authored before the integration exists.

Edit an existing scenario

  1. In Learning Studio (frontend) the LXD picks a scenario from the Scenario Manager and chooses Edit or Duplicate.
  2. The Learning Studio backend returns the file it has stored for that Learning Object, and the frontend downloads it to the LXD's machine.
  3. In the Scenario Editor, the LXD chooses Open an existing scenario, picks that file, and edits it.
  4. Exporting and uploading again follows Save and update above.

Scenario IDs

Put Learning Studio's scenario ID in the document's implementation_id field. The field already exists in the v4 format, and its description in the editor already reads "how the surrounding content system identifies this implementation." Storing the ID there means the file knows which Learning Object it belongs to even after it has been emailed or downloaded onto another machine.

  • The Learning Studio backend generates the ID once, when it creates the Learning Object. Nothing else ever generates one.
  • In the Scenario Editor, do not rebuild the ID from the title. The wizard currently falls back to a slug of the title, so renaming a scenario can change the ID the engine uses for routing. Remove that fallback.
  • In the Scenario Editor, make the field read-only when Learning Studio supplied the ID. It is editable text today, and an LXD who types over it breaks the link to the Learning Object with no warning.
  • Duplicating a scenario needs a new ID, generated by the Learning Studio backend like any other. Otherwise two Learning Objects share one routing key.
  • In the Scenario Editor, change the download filenames in the same update. Filenames are built from implementation_id first, so an ID like a GUID would make every download unreadable. Use content.title instead and fall back to the ID.

Images

In the v4 format, media is { type, src, alt } and src is a plain string. The format has no field for image data, so the scenario file can only hold a reference to an image, never the image itself. The Learning Studio backend stores the actual file, in its media library. The Scenario Editor holds only the reference string the LXD pastes in.

What each side builds

Scenario Editor

  • Read ?lo= and ?title= on load. Fill in the title, set the ID, and make the ID read-only.
  • Stop rebuilding implementation_id from the title.
  • Build download filenames from content.title.
  • Store local drafts under the lo ID, so reopening a scenario resumes the right draft.
  • Nothing new for the one-file flow — the export the LXD already uses is the file Learning Studio wants.

Learning Studio

  • Backend — create the Learning Object and generate its ID on New Scenario.
  • Backend — store the uploaded file against the Learning Object, versioned.
  • Backend — return that same file when someone edits.
  • Backend — validate on upload via the authoring service, and compare the ID and title per the table above.
  • Backend — generate a new ID when a scenario is duplicated.
  • Backend — store media in the library and return a reference the editor can use.
  • Frontend — open the editor in a new tab with the ID and title in the URL.
  • Frontend — upload and download controls on the Learning Object, and the failures[] list when validation fails.
  • Frontend — asset uploader and picker reachable from the Scenario Manager.

Questions for the dev team

  • Can implementation_id be any format? The schema only requires a non-empty string, but all 11 production documents use readable slugs, and the loader has read a scenario ID from the filename in the past. We need to know whether anything downstream expects a particular format before Learning Studio picks one.
  • Can the Learning Studio backend reach the authoring service's validation endpoint? If not, we need the v4 JSON Schema as a file so the backend can validate on its own.
  • Does a backend API already exist for creating a Learning Object? And is one scenario exactly one Learning Object, or does a scenario sit inside a larger one alongside other content? Everything here assumes one scenario per Learning Object.
  • Do media-library URLs resolve without a Learning Studio login? This decides whether the Scenario Editor can render images in a preview.
  • When can v4 accept the two fields the editor authors? Prior-scenario context was approved on 18 August and the format still has no field for it. One file depends on this landing — otherwise the options are relaxing the schema or dropping the two features.
