Writer Studio · Release Readiness

Flexible where it counts, thin where it hurts

A product read on the Writer Studio ahead of next month's release: how schemas plug in, how universal the player really is, and whether we can ship both curated “recipes” and a free-form composer. Short version — the authoring layer is genuinely universal and release-shaped; the player layer is four engines held together by copy-paste; and we already support both models today.

Audience — Product + Engineering + Leadership Horizon — Release next month Prepared — August 2026
Design history — one central claim is now false

A product read written before the Option B player convergence. Its central risk finding — “the player layer is ~4 runtime engines copy-pasted across 7 live pages” — has since been resolved: there is now one ?type=-routed player over one shared engine (scenario-live.html + js/sim-player.js), and the authored format has since moved to Scenario CML v4 on top of that. Read it as a record of the decision that drove the convergence, not as a current architecture assessment. Current record: the alignment notes.

Strong · ready in shape

The authoring layer is universal

studio-shell.js has zero per-type branches. Every schema plugs in through one contract; the rail, wizard, lints, and compiled-prompt inspector come free. Adding a type is a plugin, not a fork.

Risk · needs a decision

The player layer is not

~4 runtime engines, and the main one is copy-pasted across 7 live pages (3–4k lines each). A runner fix is an N-place fix. This is the top maintainability risk for release.

1

How a schema plugs in — the strength

A “type” is one object implementing a fixed contract (DEFAULT, sections, renderFields, compile, normalize/isValid/blank, lints, previewUrl, store). The shell reads only that surface. Adding a type is four mechanical steps:

StepWhat it is
① The type modulejs/scenario-types/<type>.js — schema + editor + compiler
② One includea <script> line in scenario-editor/ (registration order = picker order)
③ A live page<type>-live.html — where the copy-paste tax lives (see §2)
④ An index carda SIM_SCHEMAS entry in index.html with studioType
Verified: the shell holds no per-type knowledge — grep studio-shell.js for type.id === returns zero. Mix & Match (the 8th type) was added in ~a day and touched nothing else. On the authoring side, the flexibility is real.
2

How universal is the player, really — the risk

Every live page shares the low-level substrate (sim-core turn engine, sim-debrief, sim-context, sim-coach-sheet, sim-chat-history). But the orchestration — the loop that actually runs a scenario — is not shared.

On top of that, coachNode (the coach-bubble renderer) is copy-pasted across ~14 pages in 3 render styles. “Universal player” is aspirational today. The authoring shell already proved the pattern — type-agnostic, driven by a contract. The player needs the mirror image: one player-shell.js + a shared coachNode, driven by a runtime contract, with types migrating onto it. That extraction is the single highest-leverage engineering investment for a durable release.

3

Recipes and free-form? Yes — and Marshall proves it

We already ship both: the 7 curated types are the recipes; Mix & Match is the free-form composer. And the recipes aren't a different kind of thing — Marshall (Guided Arc) maps beat-for-beat onto Mix & Match:

Marshall piece (Guided Arc)Mix & Match beat
Reflection warm-upcoach-led (non-graded)
“Does this qualify?” (the law)coach-led with a right answer (hasRightAnswer + throughLine)
“What is Marshall experiencing?”coach-led
The bystander sceneroleplay
SME playbook closeplaybook

Mix & Match's beat schema is essentially a superset of Guided Arc's phase schema — both descend from the same ladder phase model. So the composer is the general case, and each recipe is a pre-arranged special case. That reframes the choice:

Option A · ship as-is

Keep them parallel

8 types in the picker; recipes are opinionated engines, Mix & Match is “build your own.” Mental model: pick a format, or compose one.

Trade-off: lowest effort, ships now — but the copy-paste tax and N runtimes persist.
Option B · converge (post-v1)

Recipes as templates over one runtime

Recipes become pre-filled Mix & Match templates (“Start from the Marshall shape”) running on one extracted player-shell. One editor, one runtime, recipes as starting points.

Trade-off: the scalable end state — collapses the copy-paste tax — but it's a migration, not a v1 task.
Recommendation

Ship Option A next month; design toward Option B. Position Mix & Match as the headline (“compose any scenario”) with recipes as proven starting points — and make the player-shell extraction the bridge that makes B cheap later. Option B is being pursued in a separate track.

4

Release readiness — prioritized

What actually gates a clean release, in order. The P0 items decide the scope of the release itself.

P0

Decide release scope — it gates everything

  • Persistence is 100% localStorage. makeStore is the single seam; publish writes a key the live page reads in the same browser. Fine for an internal/pilot release; a hard blocker for multi-user/external. External ⇒ a backend behind the existing {loadPublished, publish, saveToLibrary} surface + auth + per-org key scoping.
  • The LLM worker (Cloudflare proxy) needs productionizing regardless: API-key handling, CORS allowlist, rate limits, cost model. Today it's a shared dev worker.
P1

The two structural bets

  • Player-shell extraction — one runtime + shared coachNode, mirroring studio-shell.js. Kills the copy-paste tax and unlocks Option B. Biggest lift; phase it (migrate the ladder family first). This is the Option B track.
  • Recipes-vs-converge decision — product story, docs, and onboarding all hinge on it. Recommendation in §3.
P2

Polish — cheap, high-visibility

  • Shared collapsibleList() helper — promote Mix & Match's collapsible/reorderable list into a studioApi helper (sibling to rowsBlock), then opt every list-heavy type in (Ensemble's phases + cast, Scene Sweep's hazards, Guided Arc's topic turns). One shell addition + small per-type adoption; lifts the whole studio at once.
  • Rail de-crowding — reassign crowded sections to their own rail step (a one-line group change per type, as done for Mix & Match's Voice & Tone).
Bottom line: the flexibility is real where it counts — a new schema is a genuine plugin — and thin where it hurts: the player is four engines and a lot of duplication. We can support recipes and free-form today. The gap for a clean release is the universal player and a persistence backend, not the schema model. Ship the pilot on what exists; invest the release runway in the player-shell.
