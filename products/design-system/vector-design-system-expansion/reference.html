Vector Design System — Expansion Reference

Visual reference for proposed horizontal expansion of Vector v1.5.1. Each component section shows the current state of what the design system supports today, followed by a full variant matrix illustrating the desired variability — including states, modifiers, theme modes, and composition recipes. Variants are tagged Matrices are organized by the system primitives that drive variability — intent, form, surface context, composition modifier, and decorative palette — rather than by specific semantic states (those are product vocabulary that consumers map onto the system). Variants are tagged SHIPS (in Vector today), PROPOSED (new variant to add), or FAILS (the combination has contrast or layering issues and shouldn't be used).

Badge / Status Pill

Applied via theme="badge ..." attribute on a host element such as <span>. No element tag.

Current state — what ships today

Vector ships 8 documented theme combinations on vaadin-badge, all composable with the pill attribute. The palette covers four intents (default, primary, success, error, contrast) in soft and filled forms.

Summary of system gaps surfaced by stress-testing against real UI. The badge system is solid at its primary use case — a small label on a near-white surface. It breaks down in five places that consuming products work around with custom CSS:
  1. Warning intent is missing. vaadin-button and vaadin-notification ship a warning theme; vaadin-badge does not. Cross-component inconsistency inside the design system itself.
  2. No inverted form. A forced-white-fill variant: opaque white background + intent border + intent text. The white background insulates the badge from the host — always reads as a "card lifted off the surface." Solves the case where the default soft form's tint blends into the host (warning badge on warning-tinted card; any badge on a dark surface).
  3. No outlined form. A no-fill variant: transparent background + intent border + intent text. The host shows through. Lowest emphasis. Distinct from inverted — inverted blocks the host with a white card; outlined sits lightly and lets the host show. Use outlined when you want the badge to integrate visually with the surface; inverted when you want it to stand apart.
  4. No documented layering behavior on tinted or dark surfaces. The default soft form uses transparent tints (e.g. rgba(success, 0.10)) that bleed through host surface colors, producing unpredictable contrast. The system needs a documented matrix of which forms work on which surfaces.
  5. No composition slots. Leading icons are inlined as raw <i> with manual sizing. There's no dot variant for unread indicators. There's no documented recipe for anchoring a badge to a host element (notification dot on icon button).

Desired variability — form × surface matrix per intent

Each intent gets its own grid. Rows are the surface the badge will sit on; columns are the form variant. The cell labels show which combinations the system supports today, which are proposed as additions, and which fail the layering test (e.g., the default soft form on a same-intent-tinted surface).

Form key — what each column means
Soft
Tinted fill — partial-opacity intent background + dark intent text. The default. Low-emphasis on clean light surfaces.
Filled
Solid intent fill — opaque saturated intent background + on-fill text. High-emphasis. The badge pops off the host.
Inverted
Forced white fill — opaque white background + intent border + intent text. Insulates the badge from the host's color — always reads as a "card on the surface."
Outlined
No fill — transparent background + intent border + intent text. Host shows through. Lowest emphasis; sits lightly on the surface rather than blocking it.

Decorative palette — non-semantic colors for tagging and categorization

Intent colors carry meaning. A warning badge tells the user to pay attention; a success badge confirms something passed. When the color is decorative — a tag category, an asset class, a team identifier, a project label — intent colors are the wrong tool. The design system needs a separate palette of hue-distinct, contrast-matched colors that explicitly carry no meaning.

Use intent
When the color communicates a state or system meaning — pass/fail, active/inactive, needs-attention, completion. The palette is fixed: success, warning, error, primary, contrast.
Use palette
When the color is decorative or identity-driven — tag categories, asset classes, team avatars, project labels, taxonomy groupings. The color carries no inherent meaning; products assign meaning by mapping their categories to palette tokens.
Never mix
A tag should never use theme="badge success" just to be green. That couples the tag's color to system semantics — if the success color changes in a future theme, every "green-because-I-wanted-green" tag follows it. Palette tokens are insulated from intent semantics.

Full palette — 6 existing Vector tokens + 8 proposed additions

Expansion summary — what the design system needs to add

Deliverables, abstracted from any specific product vocabulary.
  • Add warning intent. Closes the cross-component inconsistency with vaadin-button and vaadin-notification. Uses existing --lumo-warning-* tokens — no new tokens needed.
  • Add inverted form. A contrast-rescue modifier that keeps the intent color but flips the emphasis surface. Renders as opaque host-color background + intent-color text + intent border. Solves the layering-on-tinted-or-dark-surface problem.
  • Add outlined form. For low-emphasis contexts. Transparent background + intent text + intent border. Distinct from inverted: outlined is for de-emphasis; inverted is for legibility.
  • Document the surface compatibility matrix. Which forms work on which surfaces — soft on tinted-same-intent always fails; filled on tinted-dark same-intent fails; inverted works everywhere. This is a docs deliverable as much as a code one.
  • Add composition slots: leading icon with autoscaling tokens, dot variant for textless indicators, anchor recipe for host-attached badges.
  • Expose 6 existing user-palette colors as badge themes (currently shipped as --vwc-color-* tokens but not surfaced on badge). Add 8 net-new hues to round out a 14-color decorative palette spaced across the color wheel. These are explicitly non-semantic — for tags, categories, identities, taxonomy labels.
  • Document intent-vs-palette rules. When to reach for which. Critical for preventing consumer-product misuse (a tag styled theme="badge success" just for greenness ties the tag's color to system semantics).
  • Migration guidance. Map existing theme="badge contrast" behavior to the new form vocabulary so consumers understand whether they should reach for contrast, inverted, or filled depending on emphasis goal.
